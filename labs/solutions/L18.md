# L18 参考解答

对应 [观测与诊断实验](../L18-observability.md)。实际测试、演练和审计结论以 [第 19 周验收记录](../../docs/validation-week19.md) 为准。

## 1. 为什么 JSONL 不能决定是否提交

业务事务先提交，调用者随后尝试发通知。两者之间可发生进程死亡，通知入缓冲后也可因满额、exporter 失败或 BEAM 退出丢失。即使某行带 `phase=committed`，它也不是数据库证明、工具回执或审批能力。判断成功提交需要查原事件、投影、操作台账与人工决定；没有通知不能推导没有效果。

提交前回滚不应产生成功提交观测；提交后丢响应应保持同一持久化身份和原请求去重语义。不能为了让 trace 完整而把外部导出放进事务，也不能在只读 Query 中偷偷补发执行或推进操作。

## 2. 怎样恢复同一关联而不依赖进程字典

Run trace、根 span、模型 attempt 和工具 attempt 的标识由版本化业务 ID 确定性生成。进程字典、PID 或当次 BEAM 的随机状态不参与稳定关联。trace ID 是 32 位小写十六进制，span ID 是 16 位；模型开始与结束必须使用同一 attempt，不能把每个通知名分别当成新的请求身份。

同一个 Workflow 的不同 Run 各自保有 trace。依赖、round 和 Case 归属属于跨 trace links；错误地填写跨 trace parent span 会构造不存在的父子生命周期，也容易让读者误解为能力继承。关联 ID 不授予权限，旧 generation 或旧审批不能因 ID 相同而复活。

## 3. 只有长度有限的 list 为什么仍不够

如果先对每个事件发送 cast，再在 GenServer 内裁剪列表，事件已经占满邮箱。固定 ETS 槽位和条目/字节双限额在生产者入口先准入，无法准入直接丢弃；有限 CAS 尝试避免在高竞争中无限自旋。单个原子 wake 标志合并唤醒通知，导出中的事件也不会变成后续无界 cast。

一个有限 batch、一个有 timeout 的 exporter Worker、独立有界 recent，以及有限标签聚合共同限制观察层积压。队列载荷字节采用 external-term metric，并非整个 VM 的精确内存；batch、recent 和 ETS 条目开销都须纳入边界解释。host 主动发大量诊断查询不属于事件入口的背压保证。

producer 在原子预留之后、ETS 插入之前被 kill，可能遗留有限准入 permit。容量会下降，但上界不会扩大；观察仍允许丢失。持续存在的 reserved/queued 差异需要宿主检查，`Observability.restart()` 可以显式丢弃并重建观察状态，不能假称自动无损回收。

## 4. 导出故障为什么不改变返回和异常

执行路径只做有限纯投影、原子操作与 ETS 写入；它不调用 exporter，也不做同步 SQL、文件、网络或 GenServer.call。`emit` 捕获自己的异常和退出，始终返回 `:ok`，但不会捕获或替换业务代码自己的返回与异常。

Exporter 在独立 linked/monitored Worker 内运行，observer 捕获它的退出，反向链接确保 observer 被 kill 时挂起 Worker 一并终止。Exporter 是可信宿主代码，不能自行改变 trap_exit 绕过生命周期约束。Error、raise、exit 归入有限错误计数；挂起到期会被 kill。当前批次允许丢失，然后有限退避。业务 Supervisor 不依赖 observer，observer 作为末尾 temporary child 消失时不会用尽业务重启预算。host 可显式恢复 observer，执行进程、原 claim、权限和预算仍保持原状。

## 5. 怎样解释计数差异

`admitted` 统计已进入缓冲；`dropped` 统计准入阶段满额、竞争或超大事件；`invalid` 统计 schema 拒绝。`exported` 只统计 exporter 返回成功的批次行数；`export_lost` 统计已准入但在错误或超时批次中丢失的行数。每个 exporter error 不一定只丢一行。

Recent 与 metrics 在排出缓冲时更新，因此 JSONL 失败时本地仍可能有这些行或计数。反过来，尚未排出的行、已丢事件和被 kill 的 observer 都不在完整聚合里。不能将观测计数用作 API 费用、预算余额、幂等去重或“工具恰好执行一次”的证明。

## 6. Query 的完整性与安全边界

Query 用一个 repeatable-read、read-only 事务查选定 Run 与存储归属的关联，不会执行恢复。多行历史集合使用 limit，Run 与每 Run 的预算、恢复单例由 max_related_runs 限制，Workflow/Case 归属另有固定轮次上限；报告显示截断。有界投影无法解码时应显示不可用，而不是把缺失数据当零消耗或已成功。读事实、重建事实、当前产物重新核验和授权消费是不同操作。

实时字段与 durable 投影都只选择必要的 ID、固定状态、有限错误分类、计数、版本和时间。完整 prompt、模型内容、工具名/参数/结果、路径、claim token、人工 actor/理由和异常文本不进入 export。只允许安全格式的标识仍不能消除调用方把秘密藏进合法 ID 的风险；业务 ID 本身必须由可信宿主正确选择，输出还需要原有宿主访问控制。

## 7. 审批、返工和恢复的判断

从原子持久化 Case/Workflow/Run 的归属找到多个轮次，用 links 保留版本与人工决定的来源。查询和导出不能 capture 当前文件或批准产物，历史 approved 也不等于当前输出可 release。旧批准失效、旧 claim 被撤销、unknown 留待核对以及实际扣费，都应从原台账得到相同结论。

导出器完全关闭或连续失败时，原实验仍需保持这些语义。观察器只能帮助解释已经发生或正在尝试的事情，不能成为新的执行引擎、审批通道或预算来源。

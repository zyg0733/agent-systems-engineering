# L16 参考解答

对应 [静态 DAG 实验](../L16-dag-workflows.md)。实际计数、运行结果和故障证据以 [第 17 周验收记录](../../docs/validation-week17.md) 为准。

## 1. 为什么复用已有 Run 与调度器

Run 已有事件顺序、操作身份、预算、领取、lease、fencing 和 unknown/reconcile。DAG 负责何时创建子 Run 与如何观察结果；另造一套并行执行入口会让相同工具有两套提交和恢复规则。每个节点只有一个跨崩溃稳定的 Run ID，竞争 Coordinator 继续依靠数据库领取和私有队列并发限制。

## 2. 为什么只凭 ready 数量不足以限制图的宽度

ready 集合随拓扑选择和已完成节点变化。某一轮只有三个 ready，不说明图不存在四个互不依赖的节点。当前最多八节点，枚举最多 256 个子集即可检查最大反链，明确拒绝静态宽度超过三的图。`max_parallel` 则限制实际执行并发，两者承担不同约束。

## 3. 如何保持预算和权限

定义为所有节点预留五维上限，总和不能超过工作流固定 cap。节点重试仍花自己的持久化计数；崩溃、下游延迟创建和重新启动 Coordinator 不会补充次数或重置总 deadline。未用额度不回流，因此不能把这套实现称作动态共享额度池。

依赖提供完整来源数据，宿主选项来自原定义。Session、隔离和 MCP 策略用已知 schema 往返；不把模型输出解释成 hook、queue、权限或新策略。角色名没有授权含义。Reviewer 使用自己的私有工作区和宿主批准工具，不能因为依赖实施者结果而直接接管其工作区。

## 4. 汇合为什么需要完整回执、事件序号和哈希

仅有文本不能证明是哪条 Run、哪个已提交状态产生了结果。Run ID 与事件 seq 指向来源，源哈希绑定整个成功输出及 operation ledger，bundle 哈希绑定原任务和按 ID 排序的所有直接父节点。不同分支分别保存，不覆盖彼此。

回执包含非 JSON 的 inert 值时，tagged JSON 保留 atom、tuple、二进制及 map key 类型；atom 与同名字符串不能合并。错误 operation ID、unknown 或未配对回执不能成为成功来源。超过 1 MiB 时保留原事实并显式失败，而不是裁剪到看似成功。

## 5. 失败、取消与 unknown 如何共存

明确子失败触发父图失败，等待中的节点 skipped，正在运行的兄弟停止。工作流取消先提交父图门禁，之后让子 Run 收敛；已经发送的非幂等操作可能已有外部效果，所以停止结果可以是 blocked/unknown。父图终态与 unresolved 节点同时存在是有意保留的不确定性。

核对原 operation 的证据只解决该工具结果，不代表取消无效或父图可以重开。禁止通过新 Run ID、重新发现 MCP 工具或重新连接来绕过原 unknown。结果配对、已有回执复用及人工核对沿用原恢复规则。

## 6. 怎样验证真正命中崩溃窗口

在事务提交前后分别注入进程终止，检查图、队列、子节点及事件是一起回滚还是一起存在。对于已经创建的下游，用稳定 Run ID 检查只有一条记录；对于工具效果，检查 operation 状态、外部效果次数和实际执行入口次数。只看到异常、Task DOWN 或超时，不足以证明命中目标窗口。

只读重建使用新 BEAM，从定义、事件链和投影得到相同图状态，并监测所有模型/工具入口为零。重新启动 Coordinator 的续跑是另一个有副作用动作，不能把只读重建测试和实际续跑混成同一个证据。

## 7. 同预算单 Agent 与双 Agent 能得出什么结论

先保证使用同一任务和预先固定的对应脚本、整体 cap 相同、实际分配总量相同，再比较状态、结构化意见、尝试数、工具数和耗时。双 Agent 增加独立审查这一步，不能要求完整脚本长度也完全相同；应单独报告因此增加的模型尝试。固定 Scripted Provider 只能验证这套编排执行和预算控制，无法证明 Reviewer 发现了真实模型遗漏，也无法外推生产任务质量。动态 Planner、自动返工或人工发布审批需要独立接口和验收。

相同四节点 diamond 在 `max_parallel=1/2` 下运行，只是同图串行/并行对照。单/双 Agent 对照需要真正改变子 Run 结构：一条 Run 实施并给结构化意见，与实施者加 Reviewer 两条 Run 比较。正式报告分别保留这两类证据，不能把 Worker 数量当成 Agent 数量。

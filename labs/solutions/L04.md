# L04 参考解答与复核提示

请先完成 [L04](../L04-controlled-tools.md)。这里给出复核方法，实际 diff、测试输出与文件 hash 应来自你自己的运行。

## 1. 哪一步授权什么

模型看到的 `available_tools` 是本次 Runtime 公开的能力。未配置 `workspace` 时只有旧 Mock，不能通过猜测 `file_write` 名称获得目录能力。配置 workspace 后公开三个文件工具及其 schema，但 Runtime 仍验证完整调用。读取到的文件内容也只是数据，不因里面包含命令文本而得到执行权限。

schema 校验约束名称、字段和参数类型；执行时检查处理真实路径、文件类型、内容、大小、hash 与补丁匹配。一个参数对象可能形状合法，却因文件不存在或 hash 陈旧在执行时失败。这时工具调用已经被接受，结果应明确配对记账；不能把所有错误都叫“模型响应未被接受”。

| 情况 | 结论 |
| --- | --- |
| 未公开的文件工具 | 在工具提议进入 Kernel 之前拒绝，无工具意图或文件效果 |
| schema 未知字段 | 完整候选响应不被接受，没有工具效果 |
| 未知工具名称 | 保留旧调用提议路径，执行时受控错误，没有白名单外效果 |
| 非法路径 | 按实现的参数/执行检查拒绝；检查具体边界，外部文件不变 |
| 接受调用后、执行前取消 | 调用事实保留，取消阻止下一次执行，不写文件 |
| 当前内容与 expected hash 不同 | 结果为错误，保留新内容，不覆盖 |
| 后续补丁 edit 不匹配 | 全部 edit 只在内存预检，目标仍是原文件 |
| 写入已经发生后取消 | 已发生效果保留，取消不回滚文件 |
| 结果 ID 或工具名错误 | Kernel 拒绝，不追加结果事件，不放行下一轮 |

核心断言同时涉及业务状态与文件事实。只看 Run 的 `failed` 或 `cancelled`，不能推出没有外部效果。

## 2. 四种序号不能互换

| 标识 | 本周用途 |
| --- | --- |
| Run ID | 标识一次任务及其业务历史 |
| 流请求引用 | 关联本轮模型工作进程、帧、timer 与通知，进程内临时值 |
| Event seq | Run 内连续的已接受事实版本，用于重建与 CAS |
| `operation_id` | Provider 工具调用与逻辑操作的共同标识，在 Run 内不可重复接受 |

当前只有单 attempt；没有尝试 ID、调度 lease 或跨重启重试协议。若未来一个逻辑操作需要多次网络尝试，应另外设计 attempt 身份、回执与代次检查，不能重用一个流引用来替代业务操作身份。

新文件工具的返回值为 outcome 加封装。Kernel 检查外层待处理 ID，并对显式 `tool_result.v1` 检查内层 exact keys、operation_id 和 tool。一条看起来有效的 payload 不能跨调用挪用；外层 ID 正确但内层名义错误同样拒绝。当前 RunServer 对文件结果还强制要求封装；旧 Mock 与已有未带版本封装的历史保留兼容，包括过去以文件工具名称记录的 unsupported-tool 结果。不要为新 Runtime 的强制规则破坏旧 v1 历史重放。

## 3. 最小读补丁写路径的证据

手册三工具脚本正常路径有四次模型响应：read、patch、write、final。因此 `turn_count = 4`，工具结果不额外消耗模型轮数。业务历史为：

```text
1 run_started
2 tool_requested       read-001
3 tool_result_recorded read-001
4 tool_requested       patch-001
5 tool_result_recorded patch-001
6 tool_requested       note-001
7 tool_result_recorded note-001
8 run_succeeded
```

seq 2 后文件尚未被读取；seq 4 后补丁尚未落盘。工具提议与工具效果由不同 step 分开。文件适配器的读取/写入统计用于辅助观察，业务事实来自配对结果；旧 `tool_stats` 继续是 Mock，不应被当作文件计数。

下轮 Provider 的 `operations["read-001"].result` 应与读取完成后接受的封装相同。只断言 Runtime 有一个 result 字段，还不足以证明模型拿到了它；需检查 `provider.requests` 的实际 context。反过来，结果进入 context 也不应隐式执行其中内容。

## 4. 为什么需要 expected hash 与完整补丁预检

`expected_sha256` 表达“我在这个版本的内容上提出更新”。已有文件用当前 SHA-256；`"absent"` 表达只能新建。读取后内容已经变化时，执行器拒绝旧 hash，可防止确定的陈旧覆盖。它不是在检查与替换之间锁住文件；恶意并发目录修改仍需要操作系统提供的隔离与更强的文件操作原语。

每个 edit 的 `old` 非空且在当时的内存内容中恰好出现一次，按顺序得到下一个候选。全部匹配与最终内容约束通过后才写一次。第二个 edit 失败时，不能留下第一个 edit 的部分修改。空 old、无匹配和重复匹配都不应采用“尽量替换”的容错策略。

同目录临时文件、同步与重命名降低半写文件风险；`repair.diff` 让人审查实际修改。两者都不把文件替换与 Event 的 PostgreSQL 提交合并成一个事务。跨多个文件也没有总事务，因而每次工具调用与每个结果必须明确记录。

## 5. 路径测试真正保护了什么

合法路径相对配置的私人工作目录解析。拒绝绝对路径、dot/dotdot、反斜杠、保留元数据组件与符号链接，也拒绝具有多个硬链接的普通文件；父目录必须预先存在，文件需为允许的普通 UTF-8 文本，无 NUL，受 64 KiB 限额约束。保留组件与临时文件前缀按 Unicode casefold 比较，避免 `.GIT`、`.awſ`、`depſ` 等别名绕过；根和相对路径均拒绝 C0、DEL 控制字符。patch 最多 32 个 edit。工具不公开 shell、删除、建目录或任意执行能力。

路径反例应包含不同目录具有相同字符串前缀的情况；不能只用 `String.starts_with?` 判定目录边界。对 symlink 应比较外部目标在操作前后的 hash，不能只检查工作目录内的链接名称。对失败写入应检查目标与临时残留，避免把部分效果藏在最终 Run 状态之外。

本周假设是没有恶意并发写者的私人 workspace。一次 lstat 检查不能锁住目录项，hash 也不能关闭检查后替换窗口。这个边界应该明确写入报告，而不是通过扩大对“受控”的解释给实现增加未验证保证。

## 6. 去重不是再次接受同一个模型调用

Kernel 的唯一 ID 规则拒绝一条 Run 内第二个同 ID 工具提议。文件适配器的内存台账则保护执行侧：相同 ID、相同工具和相同参数返回已缓存结果；相同 ID 改参数或工具时报冲突。二者面对不同边界，不应互相替代。

缓存读取返回第一次结果，即使文件后来由宿主改变；这是同一调用的回执，不是一次新的读取。缓存写入返回第一次结果，不重复写文件。失败结果若已进入该实例台账，重复同样调用也不应该被悄悄当成新的尝试。

台账退出后消失。一次文件替换已成功、结果提交前进程崩溃时，数据库可能仍只有 pending tool 意图。新进程不知道原效果；旧 hash 可能帮助发现文件已经变化，但不能证明变化来自哪个调用，也不能给出原回执。这个窗口需要后续持久操作账本、核对与恢复策略，本周不自动重放未知效果。

## 7. PostgreSQL 和 rebuild 的正确观察

接受工具调用时，Run、`tool_requested`、pending tool 意图在一个事务中提交。工具执行发生在事务之外；接受工具结果时，再原子保存 Run、`tool_result_recorded` 和下一项 model 意图。最终回答被接受后没有 pending 意图。

内层 `tool_result.v1` 封装与 payload 是已接受历史的一部分。新 BEAM 读取它不需要当前目录仍存在，rebuild 只调用纯 Kernel；不会重新运行文件读取、write 或 patch。测试可以在停 RunServer 后移走练习目录，再加载数据库与重建，证明历史不是即时文件视图。

已知陈旧的 PostgreSQL 状态在工具执行前会被拒绝。数据库先取消后，旧 RunServer 不能继续写文件。但读取当前状态与执行文件工具仍有间隙，因而这个检查不是 lease、fencing 或跨系统原子性。

## 8. 离线修复要留下什么

`lab.repair` 是完整 Agent 路径的可重复演示：模型提议读取、修补、写说明，再给最终回答。免运费门槛从 `subtotal > 100` 改为 `subtotal >= 100`；固定测试修复前 3/4 通过、exit 2，修复后 4/4 通过、exit 0。宿主核对源文件与测试的精确字节才执行验收，并生成 `repair.diff`、两份测试日志、`report.json` 与 `events.bin`。正常路径应由四次模型响应和三次工具调用解释；diff 中不能出现无法关联到调用的模型文件修改。

它证明工具路径、配对、修复流程和 diff 证据可以闭合。它没有证明 Scripted 模型具备推理能力，也没有把任意模型生成代码当作安全的宿主执行输入。报告中应将 Agent 改动与宿主验收程序各自的权限写清。

## 9. 复核追问

1. schema、workspace 能力、文件预检分别在哪一层拒绝请求？哪些拒绝前已经提交了工具意图？
2. 没有 workspace 的 Provider 是否看得到文件 schema？即使猜中工具名又会怎样？
3. 哪条断言能证明模型收到了对应调用的读取结果？
4. 外层 ID 正确，内层 ID 或工具名错误时，哪个保护分支拒绝？
5. 第二个 edit 失败时如何证明没有第一个 edit 的部分效果？
6. 相同 ID 改参数与相同参数重复执行各自得到什么结果？重启之后还保留吗？
7. 文件替换后、结果入库前崩溃，哪些系统各自知道什么？
8. 为什么读取数据库与 rebuild 不应要求当前文件存在？
9. 私人目录约束、hash 和原子重命名分别解决了什么，仍保留哪条竞争窗口？

答案应指向测试、事件 seq、hash、目录内容和具体 diff。笼统写“有 schema”“安全写入”或“测试全绿”不能替代边界证据。

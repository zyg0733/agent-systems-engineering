# L01 参考解答与复核提示

请先完成 [L01](../L01-state-machine.md) 的独立任务再阅读。这里给出关键结论与断言方向；项目现有测试是可执行参考，自己的实验记录仍需包含实际输出和破坏再修复过程。

## 1. 状态变化与事件

正常工具路径是：

```text
queued → running → waiting_tool → running → succeeded
```

丢回执路径是：

```text
queued → running → waiting_tool → blocked → running → succeeded
```

第二条路径多出显式核对。`blocked` 不是终态；它表达当前没有足够事实继续作决策。最终回答只能在 `running` 接受，不能跳过核对。

命令是可拒绝的请求；事件是已经被接受的事实。非法命令没有新事件，调用者持有的原状态也不会发生原地修改。比较错误元组还不够，需同时证明轨迹没有延长、状态没有被其他路径改变。

## 2. 最小的独立测试形状

下面只展示一个断言模式。其他状态应自己搭建，不要复制一个测试改标题。

```elixir
defmodule AgentSystemsLab.L01StudentTest do
  use ExUnit.Case, async: true
  alias AgentSystemsLab.Kernel, as: LabKernel

  test "未开始的任务拒绝最终回答" do
    {:ok, initial} = LabKernel.new("student-invalid")

    assert {:error, _reason} =
             LabKernel.dispatch(initial, {:model_response, {:final, "too early"}})

    assert initial.status == :queued
    assert initial.seq == 0
  end
end
```

状态是不可变值，最后两个断言说明我们没有得到一个成功状态，但单独检查旧变量不能证明所有实现都正确。主要保护来自错误返回、没有 `next_state/events`，以及对合法执行与完整事件轨迹的独立检查。

## 3. 为什么两个层面都要有操作编号规则

Kernel 拒绝重复申请编号，防止模型在一个任务中把新动作伪装成旧动作。Mock 接受同编号同参数的重复传输，是为了模拟客户端在不确定是否送达时复用稳定幂等键。二者保护的位置不同。

同编号不同参数必须冲突；否则“重试”可能静默取得不属于这次意图的旧回执。编号需要稳定绑定业务意图，不能每次网络尝试都生成新编号。本阶段只在内存范围内验证该规则。

## 4. 三种工具结果

| 情形 | 客户端观察 | Mock 效果数 | 应做的动作 |
| --- | --- | ---: | --- |
| 正常成功 | `{:ok, receipt}` | 1 | 记录结果，再继续模型步骤 |
| 效果前失败 | `{:error, reason}` | 0 | 记录操作失败，回到 `running`，由驱动继续或显式结束任务 |
| 回执丢失 | `{:unknown, reason}` | 1 | 阻塞，查询操作台账，再核对 |

`unknown` 是调用方的知识状态，不能据此推断效果不存在。查询到回执后，可以把确认结果送给 Kernel；本实验的工具台账允许查询，所以核对是可完成的。真实工具未必有同样接口，未来必须明确其核对能力。

工具操作确认失败与整个任务失败也需要区分。Kernel 记录 `{:error, reason}` 后回到 `running`，允许上层决定换方案或显式 `fail`。类似地，Kernel 拒绝超预算的模型响应；RunServer 将预算耗尽转成显式任务失败。这些策略不能藏进测试假设中。

重复提交同一编号和参数后，应看到 `requests` 增加而 `effects` 不增加。参数冲突与查询同样不应新增效果。不要把请求计数当成效果计数。

## 5. 取消和迟到结果

取消表示 Runtime 不再推进这项任务，不保证撤回外部效果。`cancelled` 与 Mock 台账里存在一条成功记录可以同时成立。迟到结果应被终态规则拒绝；如果未来需要收集迟到回执，应在独立的操作核对机制中设计，不能偷偷修改任务终态。

## 6. 确定性与恢复边界

相同初态、合法命令和选项应得到相同状态与事件。Provider 也需要显式传递返回状态，否则会重复读取旧的脚本位置。Provider 游标推进与 Kernel 接受命令是两种独立状态变化。

重放应该只应用事件。一个实用断言是：在工具已经产生一次效果后保存计数，重放同一任务事件列表，再次读取 Mock 计数，两次相等。

进程内存不是持久化存储。Mock 重启会丢失本阶段的台账；RunServer 重启也不能凭空恢复事件。监督树负责重新启动进程，不负责重建已丢失的业务事实。`rebuild` 的前提是调用者仍然持有完整、合法的事件列表。

下一阶段的关键空隙是：工具已经产生效果，但 Runtime 尚未可靠记录 outcome。需要定义 intent、操作编号、结果记录和持久化确认点，并在每个边界注入故障。仅把现有列表写入文件，还没有定义原子提交与恢复协议。

## 7. 验收时可以追问

- 你的随机命令轨迹如何保证合法？失败后能用种子和最短轨迹复现吗？
- 修改测试中的操作编号，哪一条断言会先失败？
- 如果演示全部通过但新加一个非法转换也被接受，哪份证据会暴露问题？
- 10 条固定 fixture 为什么不能代表真实模型的完成率？

能指出具体命令、事件、效果台账和断言，才算完成了机制解释。

# L17 参考解答

对应 [人工审批实验](../L17-human-approvals.md)。真实通过结论、计数与证据以 [第 18 周验收记录](../../docs/validation-week18.md) 为准。

## 1. 人工批准的是哪一份结果

批准的是一个完整 subject：Case ID、固定 Plan 哈希、轮次、generation、成功 Workflow 的 ID/seq/proof、所选产物的相对路径、完整字节及哈希、protected baselines 和 initial 元数据。只有文本 `approved: true`、一个 Run ID 或某个文件路径，都不足以说明操作者看过哪些确切字节。

请求的 expected_seq 与 subject_hash 一起承担 CAS：seq 防止丢失其他人工推进，subject 防止把所见内容与新内容混淆。request_id 承担请求去重；相同 ID 改变任何决定内容应冲突。actor 必须来自可信宿主先鉴别的身份，并属于固定 allowlist；本项目的字符串校验不能替代登录、签名或真实角色授权。

## 2. 为什么 outputs、initial 与 baselines 不能混为一谈

outputs 是本轮生成并供审阅的字节，正常工作会改变它们。initial 只检查本轮开始时的输出版本，例如新建 patch.diff 必须原先不存在。protected baseline 是补丁尚未应用的目标版本，例如 source.txt；从准入到 release 都必须保持相同。

如果把输出哈希当作不可变 baseline，模型一写入就会产生必然冲突；如果把 source baseline 当作可随输出一起重新捕获的数据，外部修改会被静默批准。分开后，输出改变触发新的 subject 和人工决定，目标基线改变产生显式冲突，只能拒绝或进入适用的新预声明轮。

## 3. 为什么恢复原字节也不能恢复旧审批

在检测到变化时清空当前 approval，并增加 generation。新 subject 包含新 generation，即使产物后来变回原来的 SHA-256，也不等于原决定仍有效。保留历史决定是为了审计，不能据此恢复已经撤销的授权。

`load/rebuild` 和幂等请求的历史响应不是文件消费授权。真正取出产物必须调用 release，且每次重试都重新检查当前来源、输出、protected baseline、generation 与 deadline。release 返回原审阅快照内的字节，消费方不应再按路径重读文件然后声称它们已获批准。

## 4. 为什么 release 不负责应用补丁

文件采样与数据库事务之间不存在跨系统原子事务。即使捕获前后都检查 source baseline，之后另一个宿主仍可能修改 source。这里采用私有工作区、严格路径、有限读取及前后检查，降低采样不一致风险；它不能代替真实补丁消费者对目标基线的原子 CAS。

本实验的 release 返回 immutable bytes 和 approval 证据，不写文件、不发布、不部署。后续消费方需要按照同一 expected baseline 做自己的受控写入；发生冲突保留证据并停止，不能用“刚才已经批准”覆盖更新后的目标。

## 5. 暂停怎样保持原权限、预算和恢复语义

暂停保存 Workflow delivery gate 并撤销已领取 claim token。原 claim 无法续租、提交 frame 或接受迟到结果；恢复通过原调度器重新领取同一 Run 的新代次。原 Session、工作区授权、隔离/MCP 策略、operation ID、已确认回执及实际扣费计数不变。

暂停不退款，后续恢复也不会得到新的 Case deadline。等待人工和暂停都消耗同一绝对时间窗。工具已经收到请求时可能产生效果，取消进程不能证明它没有执行；非幂等模糊结果仍须进入原可见核对队列。人工批准不能替代工具结果核对。

停止 Coordinator 仅停止该观察进程，其它竞争进程仍可能调度。人工暂停必须提交持久化 gate，才能在多个 Worker、多个 Coordinator 和崩溃恢复后统一生效。

## 6. 为什么返工必须预先声明

每个下一轮 Workflow、独立工作区、Session、工具策略和预算都在 Plan 创建时固定。`:rework` 只能选择下一轮，不能用模型输出改图或增权。所有轮的五维分配总和在第一次执行前就预留，即使后轮从未使用也不转给其他 Run；一到三轮的有限上限避免隐式无限循环。

使用新的 round Workflow ID 区分不同实施版本，同一轮恢复继续使用稳定 Workflow 和子 Run ID。原轮的结果与人工决定不被覆盖。全部轮共享最初绝对 deadline，因此反复暂停、返工或重启进程不能延长预算时间。

## 7. 崩溃恢复需要哪些事实

在真实事务窗口注入 kill，并检查 Case、人工请求记录、事件历史、gate 和下一轮 Workflow 是否一同回滚或一同存在。提交后调用者没有响应时，原 request_id 重试应得到同一推进结果；不能重复开新轮、重复记录决定或重置子预算。

新 BEAM 的只读审计需重建相同 Case、所属控制历史、Workflow 和子 Run，并验证模型、工具、capture、决定、release 与自动 sync 入口为零。只读历史不重新捕获文件内容，也不宣称历史批准目前仍可授权。

静态 Reviewer 输出与真人决定必须分开留证。Scripted Provider 和模拟 actor 能验证机制与故障窗口，不能证明真实模型审查质量、真实用户身份可信或生产发布已经完成。

# L19 参考解答

对应 [可重复评测实验](../L19-repeatable-evaluation.md)。实际测试、正式 cohort 与独立审计结论以 [第 20 周验收记录](../../docs/validation-week20.md) 为准。

## 1. 固定什么才有资格比较

协议包含整个 suite、每个 task、oracle、scorer、定价、分割、重复数、执行预算和测量范围，以及 Elixir/OTP/ERTS/architecture 身份。只固定随机 seed 无法固定这些条件。不同 profile 允许使用同一输入、权限与预算；修改定价、任务、golden 或 runtime 后，系统直接拒绝旧基线。

suite hash 还绑定 manifest 原始字节，因此改变空白也会改变 suite identity；task hash 同时绑定本任务文件及 scorer。内容哈希帮助发现不一致，不能证明报告作者可信。独立审计必须用保存的 Run ID、原持久化事实与实际产物重新核对。

## 2. dev 与 holdout 各自承担什么

dev 的六项用于调试评测路径；holdout 的四项由显式命令单独运行，没有共享 task ID，也不能与 dev 直接配对比较。任务、reference 与 golden 都在公开教学仓库内，宿主脚本固定给出答案。这只能证明任务分割和机制能落地，不能据此声称防泄题、真实模型泛化能力或外部 benchmark 成绩。

三项 regressed 响应与同一参考协议比较：排序 CSV 错误、正确产物后的额外调用耗尽预算、holdout 去重顺序错误。前后输入、工具许可、预算与 oracle 不变，因此门槛检查的是候选实际行为变化，不是换题或放宽评分。

## 3. 为什么另起一个评分 BEAM

执行成功与任务成功是两个条件。模型自报成功、Run terminal 为 succeeded，都不能证明文件正确；预算失败时即便文件正确，也不能把失败 Run 放行为成功。独立 scorer 在新 OS 进程只读捕获文件，以固定 hash 和大小 oracle 判定实际字节，不执行候选代码。

子进程不启动项目应用、不继承数据库/API 环境凭据、不接触 Run 的推进能力。sample ID、task hash、artifact hash、scorer hash 必须一一对应。错误配对、超时、输出超限、非零退出和畸形协议可见为 scorer error。独立 guardian 持有 Port 并监控调用者，在超时或调用者被 kill 时杀实际 owned PID 并确认退出；调用者的 try/after 在 :kill 时不会运行，关闭 Port 本身也不是清理完成的证明。

这是一段可信固定 grader 的外部进程隔离，不是针对恶意 grader 或任意生成代码的安全沙箱。同一宿主账户的恶意进程可能修改 chmod 只读文件；评分前后 hash 和 source 检查只能发现本实验范围的变化，不能代替完整 OS 隔离或认证。

## 4. 成本为什么不能只统计成功样本

错误答案和预算耗尽也发生了模型请求、输出和工具尝试。删去失败 trial 会同时抬高成功率、压低成本与延迟。本实现让每个计划样本保持在分母内，按原持久化事实统计：

```text
units = 1000 × model_attempts + output_bytes + 250 × tool_attempts
```

它是合成实验单位；output_bytes 不是 token，`usd=null`，dispatches 不计价。工具 execution attempt 与 reconciliation attempt 也不能混算。source 不可用或前后漂移时 usage 标为未知，不能把某一瞬间的部分计量当完整成本。未知 usage 保留 unknown count 和 known sum；完整成本为 null，比较 indeterminate，不能填零或认定“不收费”。

## 5. 延迟与复现应如何解释

execution、scoring 与 total 都来自 monotonic 微秒。Scoring 包含启动外部 BEAM 的真实时间；total 还包含证据读取等开销。失败样本同样参加 nearest-rank p50/p95，排序后选择 `ceil(n × p / 100)`；两次重复的 p95 就是较大的一次。

相同 profile 可重复的是任务 outcome、artifact、失败分类、持久化用量和语义签名。Run ID、OS PID、测量时长与完整 report hash 可以变化。仅有两次成功不能证明延迟稳定或统计等价。

## 6. 回归检查怎样避免平均值掩盖问题

比较同时执行总体和逐任务门槛，并输出 `(task_id, trial)` 配对变化。成功率按百分点下降检查；成本与延迟须同时超过相对和绝对门槛，严格大于阈值才越线。默认成功率下降 0 pp、成本增加 0%/0 units、延迟增加 25%/50,000 us；各延迟子项的 p50/p95 都被检查。零基线显式处理，不用除零或无限百分比。

Scorer/harness error 或未知计量会令门槛不通过，indeterminate 不能当 passed。噪声阈值是预先约定的政策，不是置信区间或显著性检验；遇到真实噪声应保留数据、解释原因并设计更多测量，不能看过结果后只删最慢一项。

## 7. 保存的汇总为什么还要重算

报告是惰性 JSON 数据。加载时重建 summary、分组、样本 hash、语义签名和 report hash，再与保存值严格比较，拒绝缺少 trial、重复 Run、串 task、未知字段和篡改汇总。合法 hash 仍不能认证事实来源，所以正式演练还独立核对原台账和 artifact。

纯 `lab.eval.compare` 不启动项目应用、Repo 或执行器，不再次调用 scorer。它可以对两个保存的完整报告作离线判断，也不能使已经 failed 的 Run 变成成功。

## 8. 完整失败与不完整批次的区别

一批包含任务失败、预算失败或 scorer error 的样本，只要每个计划 task/trial 都有结果，仍能生成完整报告；其失败保留在分母，门槛按有限分类决定。执行框架中断、目录写入失败或 suite 在运行中变化时，只保留已写证据及 incomplete status，没有有效完整报告，不能作基线。

恢复不能靠覆盖目录或复制已有行冒充新 trial。保存旧目录与 Run，重新创建新目录运行完整计划。观测输出丢失也不能补成零成本：真实计量必须来自原预算、模型录制和工具台账。

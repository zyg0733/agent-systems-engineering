# L12 参考解答：区分容量、资格与执行

## 1. 为什么有限 Worker 仍可能积压失控

Worker 上限只限制一个 Scheduler 的当前本地执行者。生产者仍可能向数据库无限新增未完成 Run，多个 Scheduler 的 Worker 容量也会相加。因此本周在显式命名队列的创建事务中检查 capacity，在领取事务中检查共享 max_inflight，并继续保留每实例 max_workers。

准入必须同队列串行化检查与写入，否则并发生产者可能同时看到“还有一个空位”并各写入一个 Run。拒绝创建要回滚整组 Run/Event/intent/配置/预算事实。blocked 仍未完成，继续占 capacity；终态空出准入名额不等于删除历史。

## 2. 租约上限为何不等于进程上限

max_inflight 衡量数据库中的有效资格。一个被 SIGSTOP 的旧 Worker 可能在 expiry 之后继续存在，新 owner 已合法接管；资格数仍合规，但真实进程数可能暂时更多。每实例 active 上限和实际退出后的槽位回收限制本地过程，数据库 fencing 拒绝旧代次迟到提交。

验收要分别记录队列有效 lease、高水位 Worker/executor/Task 数和回收中执行者。只在负载结束后看到零个执行者不能证明饱和期间没有扩张。基础 VM 进程与固定数据库连接形成独立基线，不能拿业务 Worker 的上限解释全机器进程数。

## 3. 为什么 heartbeat 不能代替执行超时

续期者可以健康运行，而 executor 永远停在一个 gate。独立单次执行 watchdog 结束这种占位：先停止并等待执行者，再用当前 claim 读取持久事实和回收。预算、lease 和 heartbeat 分别回答“还能执行多少”“谁有资格”“资格是否继续有效”，它们不会互相替代。

每任务 dispatch 预算在执行前持久扣除，新的 Worker 或新 BEAM 不能重置。它与已有 turn、模型/stream/工具预算、绝对 deadline 和 retry 限额同时约束任务。调度次数不等于模型调用、成功次数或业务效果数，报告须单独计量。

## 4. 超时以后该做什么

先停止并等待本次本地执行者，不能先释放 claim。随后读取同一个 Run/operation 的提交事实：已确认 receipt 可以接受，工具 prepare 后的模糊结果不能假装从未执行，支持稳定身份查询的目标可按原身份核对，无法证明的非幂等工具保留 blocked/manual。

没有工具台账的未完成执行明确 failed；有准备记录但结果未确认的执行 blocked，按原目标能力核对。已耗尽的调度预算不阻止结果核对。Scheduler 单次执行默认上限 30000ms，与任务固定 execution_timeout_ms、原 Run 绝对 deadline 取更早约束。超时只说明观察窗口结束，不证明远端请求终止或文件写入回滚。换 operation ID、删准备记录、重置 dispatch/retry 次数会破坏恢复证据。数据库不可用时连回收是否提交都需要重新读取确认，不能用当前进程日志填补事实。

## 5. 公平性如何说明

优先级老化按当前 intent 的数据库年龄计算 `min(9, priority + floor(wait_ms / aging_ms))`。每个有界候选页内比较有效分数与 intent ID，持久游标继续扫描下一页；它提供轮转发现，并非每轮全队列严格优先级排序。非抢占策略保持当前执行资格；执行预算配合可响应的本地 watchdog 回收挂起步骤。报告用持续高优先级输入下的服务顺序、低优先级等待和每组服务次数解释实际结果。

饥饿阈值是告警条件，不是完成期限。活跃 lease、future retry 和人工核对分别已有合理等待原因，不能误报为 Scheduler 忽略任务。指标只在观察时筛选 ready，年龄并非累计 eligible 时间，所以刚到 due 的旧 intent 也可能立刻越过阈值，应结合 retry 事实判断。观测接口只读，采样前后应保持 seq、claim、retry、operation、模型录制和效果数不变。

有界查询还需要扫描进展：若总是返回相同的 future 前缀，LIMIT 保住了每轮成本，却没有给后面的到期任务机会。测试须把可领取候选放到不可领取前缀之后，证明轮转发现可继续，同时保留扫描批次上限。

## 6. 满载该如何操作

先看命名队列 capacity、未终结数、有效 lease 与 oldest eligible wait，再看每个 Scheduler 的 active、heartbeat、回收和错误。满载拒绝反馈给生产者，停止继续输入并采用有界等待；unknown 通过核对协议处理。若有 eligible 饥饿，检查队列范围、共享 quota、老化、锁等待、扫描进展和 Worker 是否持续服务，不通过修改 priority、due 或 claim 掩盖症状。

相同队列的 max_inflight 是共享上限；单实例 max_workers 只属于该实例。历史保留、任意外部生产者、远端请求、生产吞吐 SLO、OS 沙箱和多租户隔离仍需独立设计。正式数据与命令见 [L12](../L12-backpressure-budgets-fairness.md) 和 [第 13 周验收记录](../../docs/validation-week13.md)。

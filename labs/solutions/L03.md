# L03 参考解答与复核提示

请先完成 [L03](../L03-streaming-control.md)。这里给出结论和断言形状，不替代你的运行输出、SQL 和破坏练习。

## 1. 预测表的关键答案

以下假设使用新 Run、此前没有接受响应或执行工具：

| 观察点 | Run 状态 | 模型轮数 | 操作数 | Mock 效果数 |
| --- | --- | ---: | ---: | ---: |
| 文本一半，尚无 `:done` | `running` | 0 | 0 | 0 |
| 半截工具 JSON | `running` | 0 | 0 | 0 |
| 完整工具响应刚被接受 | `waiting_tool` | 1 | 1 | 0 |
| 工具 `step` 完成 | `running` | 1 | 1 | 1 |
| 半截 JSON 时取消 | `cancelled` | 0 | 0 | 0 |
| 已产生效果后取消 | `cancelled` | 保留已接受轮数 | 保留已有操作 | 仍为 1 |

工具请求是模型提议，工具执行是后一步动作。这个分界应由两个不同断言证明：在完整响应被接受前没有操作；被接受后、下一次 step 前已有操作但没有效果。

若工具效果已发生但回执丢失，Kernel 中的操作可能仍是 `unknown`。取消只结束未来推进；保留操作记录，才不会把取消误报为回滚了外部系统。

## 2. 为什么同步 step 仍然可以被取消

“客户端同步等待”不要求“GenServer 回调同步阻塞”。RunServer 可保存调用者的 `from`、启动工作进程并返回 `{:noreply, state}`；后续通过消息消费帧，并在本轮完成或终止时回复调用者。

工作进程可以在 gate 中 `receive`，因为它只负责本轮模型生产；RunServer 需要保持自己的消息循环，接收快照、取消、帧、monitor DOWN 和 timer。如果把整轮 `receive` 搬回 RunServer 回调，gate 未释放时取消调用也排在后面，便失去了运行中控制。

合格的测试顺序是：启动执行 → 收到精确 gate → 确认 snapshot 返回 → 调用 cancel → 等到 worker DOWN 和调用者返回。先 sleep 再取消可能恰好命中，也可能根本没到模型调用。

## 3. 流通知与业务 Event 的区别

通知封装为：

```elixir
{:agent_stream, run_id, request_ref, seq, event}
```

请求引用关联一轮调用；`seq` 从本轮 `:started` 的 1 开始。订阅者只收到订阅后的通知，相同 PID 重复订阅不重复投递。结束通知是 `{:finished, status}`，例如 `:waiting_tool`、`:succeeded`、`:failed` 或 `:cancelled`。

业务 Event 的序号属于 Run，跨模型轮次连续。它只记录已接受的命令，例如工具提议、最终回答、失败与取消。一次文本流有许多实时通知，接受最终回答只增加一个 `run_succeeded`。快照保留最后 128 条流通知，不改变预算的全量计数，也不提供历史重播。

订阅者已经看到 `:done`，也不能独立证明数据库接受了响应：组装校验、预算或 `expected_seq` 检查仍可能拒绝提交。应核对 finished 状态和业务快照；持久模式用 `Storage.load/1` 确认事实。

## 4. 工具参数为什么到 done 才解析

JSON 分片边界不是语法边界，也不是 UTF-8 字符边界。把每个片段单独解码，可能拒绝合法的分片；尝试对前缀做容错解析，可能执行尚未完整表达的调用。正确路径是有界累积 → 结束帧 → 完整解码 → 对象与响应形状校验 → 预算核对 → Kernel 接受。新文本流在结束时还检查完整 UTF-8，非法字节得到 `:invalid_text_utf8`；旧完整文本响应保留原 binary 语义。

当前协议一轮只表达一个文本最终回答或一个工具提议。拒绝文本与工具混合、多个工具声明、工具声明前的参数、非对象 JSON、缺少结束以及完成后的额外帧。空 `:done` 可以形成空字符串最终回答；空文本与未完成流应分开测试。

Scripted 的 gate、sleep、crash 和 error 是测试控制项，不是可提交的工具参数或业务帧。只有普通帧进入通知和流帧计数。旧脚本仍通过完整响应适配帧工作；它不需要先转为 JSON 再改写业务参数。

## 5. 取消与迟到消息的保护

```text
本轮请求 A 活动
      │
      ├─ cancel 提交成功 → cancelled → 停止 worker / 清理 timer
      │                                      │
      │                          A 的旧帧或旧 timer 到达
      │                                      │
      └────────────────────────────── 拒绝，不追加业务事实
```

清理 timer 和停止 worker 降低后续工作，但已发出的消息仍可能留在邮箱。Runtime 需要检查活动请求身份和业务终态，不能仅依赖 `Process.cancel_timer` 或 `Process.exit`。发给已死 worker 的 release 不会生成迟到帧，因此它只是其中一条保护测试；仍需针对实际内部消息协议注入旧消息。

使用紧随注入后的同步 `snapshot/1`，让同一发送者的消息先后顺序成为处理屏障，再比较状态、事件和效果。断言“没收到意外通知”不能独立证明业务状态未被改写。旧 model timer 还应在下一轮请求活动时测试，避免只靠整个 Run 已终态而通过。

取消与完成竞争时，测试不应该强行要求某方总获胜。若完整响应先提交为 `succeeded`，随后取消被终态保护拒绝；若取消先提交，随后完成不能改变 `cancelled`。核心断言是仅一个合法终态、没有后续工具效果、事件重建与实际状态一致。

## 6. 六种预算各自测什么

| 限额 | 易漏掉的反例 |
| --- | --- |
| 输出字节 | 中文字符数小于字节数；工具标识很大；跨轮单次不超、累计超限 |
| 流帧数 | 很多空片段或小片段；`:done` 也占一帧；gate 不占帧 |
| 工具次数 | 超限提议已经被完整组装，但必须在 Kernel 接受前拒绝 |
| 模型轮数 | 工具完成不增加模型轮数；下轮预算已耗尽时不能调用 Provider |
| 模型时限 | 连续收到片段也不重置整轮截止；gate 中超时必须终止 worker |
| Run 时限 | 包含等待手动推进和 blocked 时间；旧模型 timer 不能影响新请求 |

输出字节按同一 Run 进程累计，不是每轮重新计数。流式文本与工具参数取实际 `byte_size`，工具声明还计 operation_id 与工具名；旧完整工具响应适配帧的参数按 ETF 序列化字节计量，标识也计入。不同表示方式的成本可以不同，报告必须写清用的是哪种帧，不能把这个本地资源指标称为模型 token 或金额。

“等于上限”应通过，“再多一个单位”才超限。流帧预算只算 Provider 帧，不包含 `:started`、`finished` 或 fixture 控制项。超限前可能已显示一部分实时内容，但被拒绝的完整候选不能增加模型轮数或工具操作。

各 Runtime 限额用 `{:budget_exceeded, kind}` 记录失败，`max_turns` 延续原有 `:turn_budget_exceeded`。超限帧不会先加进已接受计数，数据库版本冲突也会撤回本地候选预算变更，因此这些计数不是远程计费审计记录。时间测试需要给非目标 timer 更宽的窗口；否则本想验证模型超时，实际是 Run 总时限先到，断言可能只靠笼统的 `failed` 而误通过。

timer 表达截止后尽快处理，不提供硬实时保证。BEAM 调度、长事务或应用暂停可能延后处理。测试应等待特定原因和 worker 结束，在合理外部截止内完成；不要要求毫秒级精确执行。

## 7. PostgreSQL 应看到什么

在半截参数的 gate：只有 `run_started`，Run 为 `running`、seq=1，model 意图 pending。片段不增加 Event、Run 版本或新意图。

如果此时取消：新增 `run_cancelled`、Run 为 `cancelled`、seq=2，旧 model 意图 superseded，没有 pending 意图。这三类事实仍在 L02 的单个事务中提交。预算失败类似，只把最后一条业务事件换成 `run_failed` 并保留具体失败原因。

完整工具响应被接受时才产生 `tool_requested` 和 tool 意图；随后工具结果产生 model 或 reconcile 意图。所有成功返回的持久快照应与 `Storage.load/1` 一致，并通过 Kernel 事件重建。

并发控制者先提交了新序号时，旧 RunServer 的流可以已经显示，提交仍必须得到 stale_sequence。不得提前发布新业务状态，也不得静默用新序号重新提交旧知识产生的回答。行锁与 expected_seq 继续承担 L02 定义的职责。

持久模式在工具执行前重新读取状态，能拒绝数据库已经记录的取消；但读完后才发生的取消仍可能与外部效果竞争。这项检查不是 fencing。当前 Mock 调用短且同步，本周没有为任意慢工具实现可中途打断的异步执行。

Provider 的自动失败诊断若包含 PID、reference 等不可持久化内容，Runtime 保存有界的 `{:unpersistable_failure, codec_error, diagnostic_string}` 原因，使失败终态可以提交。显式用户提供的非法取消或失败原因仍应报错，不能把自动诊断降级规则当成任意业务命令的隐式改写。

## 8. 为什么本周还不是流恢复

数据库保存已接受事实，不保存每个候选片段、工作进程、活动请求引用、流缓冲与 Runtime 计数。换 BEAM 可以加载已接受 Run；不能从事件数恢复失败流曾消耗的输出字节，也不能把一半 JSON 接回原网络连接。

`max_turns` 已属于可重建状态；新增资源限额目前只是一个存活 Run 进程的控制。在未来设计持久恢复时，需要明确预算预留、实际消费、失败尝试和新的执行代次怎样提交。把新 worker 的计数重置为零，然后声称跨重启总预算仍生效，是错误保证。

停止本地模型工作进程也不等于真实服务已经停止计费；取消 Run 不等于撤销先前工具效果；持久 model/tool 意图存在不等于可以盲目重发。继续沿用 L01 的未知结果核对与 L02 的事务窗口分析。

## 9. 复核追问

1. 哪条测试能证明 `step/1` 等待期间 GenServer 仍可处理取消？
2. 你如何证明半截工具 JSON 没有变成 Kernel operation，而非仅仅“暂时没产生效果”？
3. 订阅通知序号和业务 Event 序号分别在哪里开始、在哪里结束？
4. 为什么停止 worker 与取消 timer 之后还需要消息身份检查？
5. 一条中文流在 5 字节和 6 字节限额下分别怎样结束？工具名是否计入？
6. 如何使模型 timer 和 Run timer 的实验互不干扰？
7. 模型已经发送 `:done`，数据库为何仍可能没有接受该回答？
8. 哪些数据换 BEAM 后还能读取，哪些消费不能恢复？

回答应指向可执行测试、精确失败原因、事件序号、SQL 行与具体消息屏障。只有 CLI 输出“cancelled”或测试全绿，不能替代这些证据。

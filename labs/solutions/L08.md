# L08 参考解答

建议先完成实验再阅读。实际测试计数、注入入口与演示证据以 [第 9 周验收记录](../../docs/validation-week09.md) 为准。

## 重试资格是多个条件的交集

错误分类描述观察到的故障，有限策略决定是否还有一次机会，工具能力决定重复投递是否安全，claim 与当前意图决定谁可以推进，预算和 deadline 决定还能不能消耗资源。它们不能互相代替。

暂时不可用可能允许重试，但此刻还在退避、已取消、总预算耗尽或 lease 失效时，仍不能调用。相反，工具回执丢失即使源于暂时网络问题，也不能仅凭错误可恢复就重发非幂等业务。

永久 schema/权限错误应该保留具体原因并停止。Run deadline、输出预算、取消等约束不会因为 retry policy 存在而消失。模型单请求等待超时可以在策略内再请求，与整个任务总时间耗尽是不同事实。

## 第一次尝试也占用次数

`max_attempts: 3` 表示最多总共 3 次，不是先执行一次再额外重试 3 次。第 1 次失败后按 base delay 安排第 2 次，第 2 次失败后按 2 倍 base delay 安排第 3 次，第 3 次失败就耗尽。指数间隔封顶，并受首次尝试起算的总窗口与 Run 绝对 deadline 共同约束。

候选 due 达到时间上限就不能再安排。重试窗口不是每次失败后重新生成的时长；否则无限次失败仍可以不断延长“最后机会”。实验使用确定性间隔，以便断言具体 due；这不等于已经提供生产环境的 jitter 或全局拥塞控制。

## 持久 due 才能跨进程成立

worker 内 sleep 只表达一个进程的等待，不表达任务已提交的下一步资格。当前实现保存失败尝试、首次时间、due 与停止原因，时间来自数据库。未到期时显式 resume 返回等待快照并释放资格，不循环等到期；新进程读取到的计数与 due 必须相同。

`resume` 返回等待快照，`step` 返回 `retry_not_due`，都不开始新的尝试。尝试 reservation 已在效果前提交；同 token 重复 reserve 被拒绝。新 claim 接管未完成模型/查询时先记录旧尝试放弃并退避，工具则进入 unknown，不把旧进程退出解释成没有效果。

到期也不自动产生效果。下次显式 resume 重新验证当前历史、意图、claim、预算和能力，才可能开始下一次尝试。本周没有后台定时 daemon，因此“到了 due”与“已经再次执行”应分别观察。

新策略保存在独立 sidecar，原 Recovery 配置 v1 继续严格检查原形状。未显式启用的旧任务沿用第 8 周语义。兼容性不应通过忽略未知字段或用新默认值改写原授权来实现。

## 模型失败仍然消耗资源

cursor 代表已接受的离线模型脚本位置，失败请求不会推进它。一次逻辑响应可以有多个请求 attempt，但只有完整通过校验并提交的响应进入录制；不能把两次失败流拼成一次完整回答。

失败请求产生的输出字节和总 model attempt 机会仍然保留。当前工作的重试上限、整个 Run 的 `max_model_attempts`、Kernel 的已接受 `max_turns` 是不同约束；使用其中任意一个替换其余两个都会产生漏洞。重启时清空其中的资源进度，会让故障变成配额重置入口。

结果 COMMIT 后 ACK 丢失时重新读取已接受事实，不能认为 caller 报错就又请求一遍。同样，超时之后的迟到响应必须重新通过当前资格与 seq 校验，不能覆盖取消或已提交的新事实。

## 工具超时首先产生知识问题

超时说明 Runtime 在限定时间内没有拿到完整结果，不能证明外部没有执行。杀掉本地等待任务也不证明远端效果被撤销。非幂等操作在效果与回执之间的窗口必须保留 unknown；自动重投会把一个信息不完整的问题变成第二个业务效果。

只有能证明效果前失败，并且能力与策略均允许时，才可以安排再次投递。幂等 Mock 重投保留原 operation ID 和精确参数，attempt 单独增加；同 ID 更换参数会冲突。幂等保证不授权无限尝试，也不能绕过 claim 或预算。

可权威查询的工具先查询原 operation 回执。query attempt 不增加业务效果。文件内容相同、临时缓存未命中或 Runtime 结果 Event 不存在，都不足以证明某次文件操作的外部结果，因此一般文件歧义仍需人工核对。

## 队列让阻塞可见，不替操作人作决定

核对队列由已验证的 blocked State、当前 reconcile 意图与工具 ledger 派生。这样不会出现“队列表写了 completed，Kernel 仍 blocked”的第二套事实。list/get 和 CLI 保持只读，不能领取或调用工具；读取前后的 seq、claim、attempt 和效果计数应该完全不变。

显式 reconcile 可以通过权威回执解除 unknown。无法查询时保留 blocked，可信操作人提供绑定原业务身份的结果与非空证据，作为新的审计事实提交。人工证据不会消除原 unknown attempt，也不会撤销外部效果。程序只验证证据形状和绑定，不能保证人的判断正确。

只读查询也可能暂时失败或超时，因此可查询任务的自动核对使用独立 `:reconcile` journal，受有限次数、due 与自身 elapsed 窗口约束。耗尽表示自动查明的机会用完，不能推导业务失败，任务仍在队列。人工确认不消耗这个配额。执行 Run 已超时仍可核对既有效果，但核对成功不重置 Run deadline，也不允许继续产生新的模型/工具执行。

核对成功、失败或取消后，任务应离开当前待核对队列；旧 attempts 与证据仍然保留。直接删除队列项、改 projection、换 operation 重发，都不能代替核对。

## 正确的故障证据同时检查没有发生什么

仅断言最后 succeeded 可能掩盖提前重试、额外模型请求或重复业务效果。每个探针应同时断言有限次数、持久 due、预算连续、旧 token 被拒绝、业务效果不重复，以及 unknown 在队列中可见。

COMMIT 前后要分开：前者未接受转换，后者事实已经成立但 ACK 可能丢失。真实 kill 后用新进程或新 BEAM 读取，才能排除内存状态的帮助。只读 History/checkpoint 与 queue 的零效果断言继续保留；执行恢复允许显式产生新效果，并不授权所有读取入口自动恢复。

有限耗尽、可见阻塞与明确不兼容错误都可以是保护正确性的结果。本周离线故障脚本、持久 Mock 与本地受控文件工具没有提供任意远程 API 的 exactly-once、真实模型连接续接、全局公平调度或文件回滚。

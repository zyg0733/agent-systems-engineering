# L09 参考解答：从故障窗口完成 P2 验收

对应第 10 周。正式证据以 [P2 故障报告](../../docs/p2-fault-report.md)、[第 10 周验收记录](../../docs/validation-week10.md) 和 `artifacts/week10-p2` 中的原始审计为准。解答关注断言为何成立，不能用手写预期值代替实际运行。

## 1. 通过的含义

一次 probe 通过，表示在指定边界真实终止调用进程后，持久状态与正确恢复决策一致。验收允许最终成功，也允许按场景正确停在等待退避、预算耗尽或待核对。尚未查明且未取消的 manual unknown 必须保持 blocked 并可见；把它强制推进成功会违反验收条件。

当前 `lab.p2` 的 16 窗口均构造可确认结果，最终断言 succeeded、effects=1、queue=[]；其中 `manual_after_receipt` 已在故障前取得人工确认，恢复只补接受事实。它的最终空队列不是“未查明 manual unknown 自动解决”的证据。仍 blocked 的反例另取 L08 第 6 节人工确认之前的快照，或相应禁止重投保护测试；提交时分开说明。静态预期计数是每轮 16 probe / 17 kill（双崩溃窗口多一次），1 轮和 20 轮的跨 BEAM probe 均为 2；用本次 report 核对，不能把这些预期写成实测。

保留三组比较：注入前 `initial.bin`、故障后首次只读采证 `before.bin`，以及明确恢复或保留人工交接后的 `after.bin`。其中都需要原始 Event、Recovery 进度、retry、intent、operation 与 attempts；`crashes.bin` 单独保存实际 caller 退出和 claim。只保存最终 State 无法分辨“复用了原回执”和“重复执行后恰好获得相同结果”。

## 2. 为什么工具成功后还能安全继续

目标效果提交、本地 receipt 确认和 Kernel 结果接受是三个边界：

- 可查询幂等 Mock 以同一 Run/operation 及参数取得稳定回执。重复投递可以新增 attempt，但不会增加第二个业务效果。
- 已确认的本地 receipt 可以复用。即使 caller 未收到 ACK，也先读取它，再将缺失的 Kernel 事实提交。
- Kernel 转换 COMMIT 后，Event、投影和下一意图已经存在。接管者读取当前 seq，继续下一项工作，不重复接受旧结果。
- 文件或不可查询业务缺少上述权威契约时，prepared 之后失联就存在未知效果。保留 unknown 与 reconcile 意图，等待可信证据。

文件内容一致不能证明 operation 完成；持久 Mock 的教学效果计数也不能替代业务契约授权。恢复决策必须能指出所使用的回执或核对证据。

## 3. 为什么二次崩溃没有重置恢复

恢复者与初始 worker 走同样的持久协议，不存在一个可以绕过审计的“恢复快捷路径”。新 owner 领取原意图、继承原 operation、预算与 retry journal，后续 owner 再次执行相同判断。

第一与第二个 caller 的 KILL 均发生在确定 gate 后；监控真实 caller 退出，再等数据库 lease 自然到期。第三个 worker 的 claim 具有新的 token 与代次。旧 token 不能确认 receipt、接受 Event 或释放 successor 的 lease。每一步新增的 attempt 留在原 journal，不能覆盖先前的 prepared/unknown。

若在查询得到回执后、接受 reconciliation 前再次退出，下次核对复用已保存回执；若 reconciliation 已 COMMIT，只读状态已不再 blocked，不能再接受第二次核对 Event。这个区别必须用提交前后对照证明。

## 4. 时间与资源为何不会凭重启恢复

Run deadline 在创建时固定；每个模型 attempt 在启动前预留并持久扣账，frame 在 ACK 前扣输出。没有接受的响应不推进 cursor，也不会得到录制，但已花费的尝试和输出仍保留。

Retry journal 在调用前预留 ordinal，失败后保存 first-attempt、分类、due 与耗尽原因。预留后崩溃不返还 ordinal；模型/查询接管先记录 abandonment 和退避，工具接管尊重模糊效果。due 已提交后崩溃，新 BEAM 读取同一个绝对时间。提前 resume 快速返回原等待状态，不新增 Provider/工具调用。

显式查询可以在执行 deadline 以后核对已有效果，但其次数与 elapsed 窗口仍有限。成功核对只记录观察事实，不能使已过期 Run 获得新的执行时间。

## 5. 操作员如何避免二次业务

先读 [恢复运行手册](../../docs/recovery-runbook.md)，对齐 Run、seq、operation 和参数，再决定 resume 或 reconcile。`lab.rebuild` 是纯重建；`lab.recover` 和 `lab.p2` 创建新的演示；已有 Run 必须用原 ID 通过 Recovery 续跑。

manual 核对先固定预期 seq，再取得新 claim，用原 operation 与 tool 包装结果，附可追溯证据。如果期间其他 worker 已推进，领取结果的 seq 不再相同，应释放自己的当前 claim 并重新采证；旧 claim 返回 stale/expired 时丢弃它。不能忽略冲突，也不能通过更换业务 ID 绕过。

确认后检查：只出现一次核对 Event；原 unknown 与证据保留；当前队列离项；后续 resume 仍受原 deadline、预算、cursor 与策略限制。取消只改变未来动作，不能宣称撤销已有效果。

## 6. 保护断言

| 有意破坏 | 应触发的失败 |
| --- | --- |
| 不验证 claim token / generation | 旧 owner 迟到写入或错误释放新 lease |
| 接管后重新创建 operation | 目标身份、参数绑定或业务效果唯一性 |
| prepared 文件自动重写 | manual unknown 与禁止自动投递 |
| 绕过 receipt 复用 | 已确认回执恢复窗口与目标调用次数 |
| COMMIT 后再单独推进 cursor | Run/Event/录制/progress 原子性与新 BEAM 一致性 |
| 重启重新分配预算或重算 due | 跨进程资源保留、提前调用与有限耗尽 |
| list/get 自动查询或执行 | 纯重建/队列读取零效果与审计不变 |
| 吞掉不兼容 schema 或损坏记录 | fail-closed、错误可见与零执行 |

这些保护测试的作用是拒绝错误实现。它们不证明所有外部系统具备 exactly-once，也不证明任意主机故障或网络时序都已覆盖。P2 可以冻结当前明确契约下的恢复行为，后续扩展真实 Provider 或外部工具时仍需重新验证其能力与失效边界。

# L13 参考解答

对应 [数据库断连与 P3 实验](../L13-database-outages-p3.md)。该文件给出判题依据，具体计数与执行结果以 [第 14 周验收记录](../../docs/validation-week14.md)、[P3 报告](../../docs/p3-report.md) 和原始报告为准。

## 1. 事务函数报错以后，是否应该重发

不能只根据报错决定。提交前连接断开可能让事务回滚；COMMIT 已经到达数据库而成功回报丢失时，服务器可能已经保存事实。恢复流程应查询原 run_id、seq、intent 和 operation，校验历史与固定配置，再依照当前状态继续。新的模型或工具效果需要新的有效 claim，不能从一个未确认的领取结果自行开始。

创建事务是原子边界，失败时不能残留部分 Run/Event/intent；已经确认的既有事件也不能在重连后回退。成功回报丢失不会授权生成新业务身份重试。能否确定结果，取决于原身份及持久事实，而不是错误文案。

## 2. 为什么连接池自动重连还不够

连接池恢复的是与 PostgreSQL 通信的能力，不会自动重建 Worker 的业务所有权，也不知道外部工具效果是否发生。本次数据库 helper 使用独立、有限的执行进程和时限，避免控制面阻塞；数据库退避限制重新尝试的频率。新的领取仍需通过事务，续租仍需当前代次及数据库时间，业务 retry 仍读原持久策略。

合格答案必须区分数据库基础设施错误和业务 provider/tool 失败；不应因一次查询错误扣一次新的业务 retry，也不能把 Worker 退出直接登记为工具确定失败。

## 3. renew 回报未知时，为什么不立即 release

本地无法证明事务到底是否提交，也无法仅凭内存里的原 expiry 决定当前权威。停止并等待本次 executor 退出后，保留持久资格直到数据库事实明确或 lease 自然到期，让后继用新 generation 接管。盲目 release 会把资格变化和本地执行停止的顺序混乱；即使释放入口有 CAS，结果未知也应作为恢复条件，而不是继续执行业务的理由。

旧执行回到系统后仍必须验证原 token/generation/seq 与数据库 deadline。SIGSTOP/SIGCONT 证明 lease 到期不能证明旧进程死亡；fencing 才决定迟到写入是否被接受。

## 4. 工具效果已经发生，却读不到 receipt，应当如何处理

保留原 operation ID 和参数哈希，读取已有 receipt 或按该工具的查询能力核对。可查询 Mock 得到证据后可以继续；无法确定时 blocked/manual，不能自动重新执行非幂等效果，也不能换 ID。真实效果数来自目标台账或明确证据，不能按客户端 success 日志计数。

manual 占用准入 credit 是有意保留未知工作。超时和断连不是清理业务台账、重置 budget、删除 retry 或扩大权限的授权。人工确认也必须带原绑定身份和证据，并接受当前 claim/fence 检查。

## 6. P3 判题与扣分点

合格交付同时包含五项数据库窗口、W11—W13 组件证据、事件/代次/效果审计、资源高水位、源文件 manifest、选型 ADR 和恢复运行手册。报告需能从每项结论返回原始逐次记录，保留失败与预期 manual，不能只给总 success 数。

出现下列任一行为，应判为核心恢复不变量失败：没有数据库确认就启动新业务；提交回报丢失后换身份重发；旧代次覆盖；重复真实效果；已确认事实消失；未知结果被自动删除或隐藏；连接失败热循环导致 helper/Worker 无限增长。

开发默认重复 2 次与 v0.1 建议每点至少 20 次分开报告。数据库高可用、跨区、任意外部 exactly-once 和出版定稿都不在当前完成声明内。第 20 章仅是和本次已验证代码对应的初稿，仍需他人执行、试读反馈与技术审校。

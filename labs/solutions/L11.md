# L11 参考解答：旧 Worker 复活后为何不能覆盖新状态

对应第 12 周。可执行入口和证据见 [L11](../L11-leases-heartbeats-fencing.md) 与 [第 12 周验收记录](../../docs/validation-week12.md)，设计依据见 [ADR 0011](../../docs/adr/0011-leases-heartbeats-fencing.md)。

## 1. 三个问题需要三个机制

Lease 决定下一位消费者何时有资格领取。Heartbeat 让仍活跃的执行者尝试延长当前资格。Fencing 在效果或提交边界检查调用者是否仍是当前代次。只有领取互斥，没有写入 fencing，暂停的旧 Worker 就可能在接管后恢复并提交它记住的结果。

Heartbeat 成功只表示某次续期 COMMIT；过期后不能用原 token 复活。重新领取产生新 token，并递增原 intent 的 generation。所有这些时间判断均以 PostgreSQL 当前时间为准，调用者传入的 expiry 不是授权来源。

持有行锁也不能代替时间资格。续期在初次 verify 后暂停，恢复时原 lease 可能已经过期；如果 UPDATE 直接写入 `now + lease_ms`，旧 token 就被复活。现在 UPDATE 自身检查原 expiry，且在写入时计算新截止时间；跨过原 expiry 返回 `:claim_expired`。测试使用 `:before_renew_write` gate 和真实时间复现这个窗口。

Heartbeat timer 的 reference 只保证 Worker 不处理过期或重复 tick。`heartbeat.sequence`、ACK monotonic time、duration 与 age 都是本进程诊断；首次 ACK 前为空，重启后丢失。它们能解释续期延迟，不能替代数据库的当前 token/generation/expiry，也不能跨 BEAM 比较绝对 monotonic 值。

## 2. 为什么暂停整个独立 BEAM

仅暂停 executor 时，Worker 控制过程仍可续期，数据库看见的 owner 一直有效。它能验证执行和续期独立，但不能验证“失去资格后旧执行复活”。SIGSTOP 整个子 BEAM 同时冻结调度器、续期者、执行器及模型/工具子任务；数据库与父进程继续运行，原 expiry 才能自然到达。

恢复后的 Heartbeat 可能先发现资格丢失并终止 executor。这是正确清理，却无法单独证明迟到写入的校验有效。因此测试保留内部控制 gate，让旧 executor 真正尝试提交，再让控制过程观察 lease 丢失。每一步都留下实际返回与数据库快照，不能拿构造出来的旧 claim 返回值代替执行证据。

## 3. 为什么必须在同一个 seq 上验证

如果 successor 已先提交，当前 seq 已变化，旧结果会因 seq CAS 失败；即使删除 token 校验，该测试也可能继续通过。同 seq 场景让 successor 只领取、不推进，保留相同 intent ID 与 seq：旧调用携带的唯一过期部分就是 owner/token/generation。拒绝后 successor 仍然有效，才证明资格隔离没有被 seq 变化掩盖。

还要单独测试 successor 提交后的窗口：先保存新状态与录制，再放开旧模型结果；旧调用不能覆盖输出或 cursor，也不能释放下一 owner。两种窗口相互补足。

## 4. 为什么旧 release 与旧 renewal 也是写入

迟到结果之外，旧清理逻辑也可能损坏接管者。若 release 只按 intent ID 清空 claim，会撤销新 owner；若 renewal 只检查 owner 或把过期时间向后写，会复活旧资格。两条路径都应在同一 Run/Intent 锁下校验完整当前凭证和数据库 expiry。

不能把调用返回 `:stale_claim` 当作唯一断言。需要读回 successor claim，比较 token、generation、expiry，并继续用新资格执行，证明错误清理没有留下隐藏破坏。

## 5. 为什么 receipt 与 unknown 仍然保留

效果之前失去资格，受控执行边界可以拒绝尚未发生的动作。效果之后失去资格，拒绝迟到 receipt 不能撤销已发生的动作；新 owner 要读取原 operation 和目标能力，按同一身份核对，或保留 unknown。receipt 已确认但 Kernel 尚未接受时，接管者复用已确认事实，不再次执行工具。

本仓库把受控效果前的资格检查与本地事务锁结合，也让 DurableMock 绑定稳定的 Run/operation/参数。这个受控目标不等于任意外部服务。一个独立远端若只检查业务幂等 key，可能阻止同一操作重复效果，却未必能拒绝不同操作的旧代次；真正的目标 fencing 需要目标自身保存和比较正确作用域的代次。

文件不具有可查询的业务回执。即使磁盘内容正好等于预期，也可能有其他写入者或此前效果。未知结果保留 manual 队列，不能从 lease 到期推导安全重发。

## 6. 保护断言

| 有意破坏 | 应触发的失败 |
| --- | --- |
| 只在 claim 时校验 token | 同 seq 旧结果能够覆盖 successor |
| 续期接受已过期 token | 旧 owner 在接管前后复活 |
| verify 成功后 UPDATE 不检查原 expiry | 暂停跨过 expiry 的调用复活旧 token |
| 处理过期 timer reference 或重复 tick | 多余续期扰乱节奏和诊断 |
| release 仅按 intent ID 清空资格 | 旧进程清理撤销 successor claim |
| 使用 claim map 的 expiry 作为唯一依据 | 续期后的合法工作被误拒，或伪造未来 expiry 获得执行 |
| 工具只准备时校验资格，效果前不重验 | 被接管的旧执行继续产生新效果 |
| 只测试 successor 已提交后的 seq 冲突 | 删除 token 校验仍可能不被测试发现 |
| 只暂停 executor，Heartbeat 继续运行 | 没有发生租约到期与真实接管 |
| 用 SQL 修改 expiry 加快实验 | 未验证真实时钟与续期停止窗口 |
| 效果后失联就重发非幂等工具 | 模糊结果被掩盖，可能重复效果 |
| 清理时只发 TERM 给停止态子进程 | 子进程可能仍停止，实验无法可靠收尾 |

合格报告把 signal 次数、delivery、attempt、已接受结果和目标效果分开。所有重复轮次都须有可追踪结果，失败时保留证据并使命令失败。验收通过只覆盖声明的单机故障模型；数据库断连、独立远端 fencing、背压与公平性仍需各自实验。

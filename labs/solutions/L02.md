# L02 参考解答与复核提示

请先完成 [L02](../L02-transactions.md) 的独立实验。这里解释关键结论与断言形状，不替代自己的数据库输出和破坏再修复记录。

## 1. 四个故障结果

| 故障点 | 数据库事实 | 客户端观察 |
| --- | --- | --- |
| create，COMMIT 前 kill | 没有新 Run、Event、意图 | 未收到成功返回 |
| create，COMMIT 后、ACK 前 kill | 新 Run、首个 Event、model pending 意图完整存在 | 未收到成功返回 |
| dispatch，COMMIT 前 kill | 完整旧投影、旧事件和旧 pending 意图保持 | 未收到成功返回 |
| dispatch，COMMIT 后、ACK 前 kill | 新投影和新事件存在，旧 pending 已 superseded，新意图与新状态对应；终态没有新意图 | 未收到成功返回 |

“同时存在或同时不存在”对首次创建直观成立。对已有任务，应表达为“旧版本完整保留，或新版本完整提交”，不能把提交前回滚解释成删除整个任务。

`before_commit` 只说明事务内的写入已经执行，不说明其他连接可见。`after_commit` 在真实提交之后，函数返回之前。两个 hook 位置相近，语义却正好位于原子提交边界两边。

## 2. 每条成功转换留下什么

Run 投影用于读取当前状态；Event 用于解释和重建已接受的事实；调度意图记录从该版本出发下一步需要做的工作。三者各自有用，不能用“投影存在”代替另两项。

开始任务产生 `running` 和 model 意图。接受工具提议产生 `waiting_tool` 和 tool 意图。工具结果未知产生 `blocked` 和 reconcile 意图。确认结果后回到 `running` 和 model 意图。终态没有 pending 意图。旧意图保留为 superseded，使当前扫描不会继续调度旧版本。

意图存在不等于已经执行。本册使用的 Storage 接收、转换和 `pending_intents/0` 读取路径没有申请 Worker claim、lease 或 fencing，也没有启动后台重试或自动核对；后续 Recovery/Scheduler 实验才引入这些执行协议。`pending_intents/0` 只是读取已提交待办。

## 3. 合格崩溃测试的形状

每条测试应包含以下步骤，而不是靠时间猜测：

1. 使用真实测试数据库，选取独立 Run ID；不使用包围整条测试的 Sandbox 事务。
2. 在独立、受监控进程中调用 Storage。hook 到达目标阶段时通知测试进程，并等待继续消息。
3. 测试收到准确的 PID 与阶段后，执行 `Process.exit(pid, :kill)`，等待对应 `DOWN`。
4. 从测试进程或另一连接读取数据库，断言三类事实与预期版本相符。
5. 断言没有收到 Storage 的成功返回，并清理自己的数据。

`raise` 通常允许库沿异常路径处理事务；`:kill` 直接终止 BEAM 进程，不运行该进程的清理回调。两者都值得认识，但只测 `raise` 不能替代请求的崩溃验收。

SQL Sandbox 的外层事务会让内层调用的“提交”仍受测试拥有的事务控制。由此得出的其他连接可见性、kill 后回滚与 ACK 结论可能与实际业务运行不同。无 Sandbox 的测试用唯一数据和显式清理换取真实 COMMIT。

对 rollback 后的查询，数据库连接可能尚在处理所有者退出。有限重试可以等待清理完成；屏障和 `DOWN` 负责确定故障位置。任意 sleep 无法证明调用已走到 COMMIT 前或后。

## 4. expected_seq 与并发

两个调用者基于 seq=1 作决策。第一个持锁调用检查到 1，提交后 seq=2；第二个获得锁后，必须发现 expected=1、actual=2 并拒绝。最终只追加一个事件。

如果只拿行锁却不检查 expected_seq，第二个调用者可能在读取新状态后，把一条基于旧知识生成的命令也提交。行锁保证排队，版本检查保证决策前提未过期。

这仍然不是 Worker fencing。本册路径没有跨长时间外部调用的执行代次；数据库锁会在本次事务结束时释放。后续持久恢复实验在提交结果时还需验证执行权。

## 5. 为什么 ACK 不能当作全部事实

数据库完成 COMMIT 后，调用进程可能来不及把结果交给父进程。此时客户端不知道成功与否，数据库知道。使用稳定 Run ID 查询提交事实，才能消除这项不确定性。

同一旧序号重发命令应被版本检查拒绝；但版本冲突本身还不能证明数据库里恰好提交了调用者原本想要的那条命令。应加载事件，核对操作编号、输入或最终结果。不要把“序号前进了”自动解释成“我的动作成功了”。本阶段还没有一个适用于任意接收请求的业务去重协议。

如果换一个新 Run ID 重发，数据库会把它看作另一项任务。稳定 ID 是核对条件，不能在不确定窗口中随意更换。

## 6. 进程崩溃与持久化配置

本实验 kill 的是应用调用进程，PostgreSQL 服务器继续运行。它证明原子性、连接清理后的回滚，以及提交不依赖调用进程继续存活。换 BEAM 后读取证明数据不在原 BEAM 内存中。正常重启 PostgreSQL 进一步验证数据库数据目录被再次使用。

PostgreSQL 的 WAL 与持久化配置决定数据库如何确认提交。`synchronous_commit` 控制提交确认等待级别；`fsync` 控制是否要求操作系统将写入可靠持久化。记录配置是说明保证前提的一部分，不是完成所有存储故障实验的替代品。

本实验不验证数据库主机突然断电、设备缓存是否诚实、介质损坏、副本故障切换或备份恢复。结论应只覆盖实际故障模型。

## 7. 仍然存在的外部效果窗口

```text
事务 A：提交 tool 意图
             ↓
事务外：工具产生效果
             ↓  ← 此处调用进程可能退出
事务 B：记录 outcome、更新 Run、写下一步意图
```

事务 A 不会丢掉已接受的待办，但也不能独立消除事务 B 前的未知窗口。新 Worker 扫到意图后，如果直接重发外部写操作，可能重复产生效果。

稳定 operation_id、外部幂等语义、可查询的持久回执和核对协议分别解决不同条件下的问题。L01 的 Mock 在同一个存活进程中演示了这些语义；Mock 重启后的空台账不是原操作未发生的证据。Provider 游标也没有因为 Run 入库就自动持久化。

因此不能把当前代码称为工具 exactly-once Runtime，也不能把 `storage: :postgres` 理解为任意崩溃后自动安全续跑。恢复先还原已提交事实，再由有定义的协议决定下一步。

跨 BEAM 读取还受 Codec v1 的词汇边界约束。`:safe` 不会为数据库字节创建新 atom；业务负载若依赖只在原 VM 动态出现的 atom，接收 VM 可拒绝它。使用字符串表达任意业务值，显式处理格式版本，优于通过不安全解码绕过失败。PID、函数和进程引用属于运行时资源，也不应该被保存成可恢复业务事实。

## 8. 破坏练习应暴露的原因

- 将意图写入移到第二个事务，会在两次提交之间制造“业务事实已提交，但无人知道要继续”的空隙。
- 删除版本检查，使旧决策也可能被接受；终态校验有时恰好挡住它，不能用一次碰巧失败证明版本检查可删。可选用非终态转换展示差异。
- 不 supersede 旧意图，使扫描同时返回多个版本；消费者若只按 Run ID 去重，也掩盖不了意图事实错误。
- 提前 ACK，使客户端已获成功的任务仍可能因随后的回滚消失。
- 不核对事件和投影，会把部分写入或错误迁移伪装成正常状态；load 应暴露不一致，不能偷偷修正并掩盖损坏。

## 9. 验收追问

1. 你的 after_commit 测试如何证明真实 COMMIT 已结束，而不是内层函数刚返回？
2. 在 dispatch 提交前 kill 后，旧意图为什么仍然应为 pending？
3. 看到版本冲突后，怎样证明提交的是自己那条命令，而不是另一个调用者的命令？
4. 如果 PostgreSQL 暂时无法连接，调用方没有收到确认，应该报告未知、失败还是成功？还需要哪项查询证据？
5. pending 扫描能发现工作，为什么还需要 claim、lease 与 fencing？
6. 哪一条测试可以防止下次重构把意图写入移出事务？

回答应指向提交位置、数据行、事件序号和独立断言。只有终端中一行“全部通过”，还不足以说明理解了事务边界。

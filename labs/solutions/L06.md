# L06 参考解答

建议先完成实验再阅读。本周实际计数与产物以 [第 7 周验收记录](../../docs/validation-week07.md) 为准。

## 重建为什么没有效果

Kernel Event 是已经接受的事实。History 按连续 seq 使用纯 Kernel.apply_event 演进投影；`tool_requested` 只把 operation 置为 pending，`tool_result_recorded` 只记录历史观察。没有调用 Provider、Mock、Gateway 或 Files 的分支。因而 `waiting_tool` 或 `blocked` 的重建结果可以保留未解决操作，而不尝试把状态“推进到完成”。

新进程测试需要比“函数返回了正确文本”更严格：比较完整 State，并跟踪 Provider 与工具入口调用次数。状态里包括 max_turns、turn_count、seq、pending 指针、完整参数与回执、终态原因。只比较 status/output 会漏掉旧调用 ID 错配、未确认效果被抹去和配置差异。

重建没有生成新的 Event。若一个函数遇到 pending 工具时执行工具、遇到缺失结果时重发请求，它就是执行恢复，不再是本周的只读重建。恢复需要独立的 ownership、幂等、效果台账与未知结果处理协议，本周没有用 checkpoint 省略这些条件。

## 历史与版本应该怎样拒绝

必须按收到的顺序验证历史，不能先排序或去重。缺口表示缺失事实，重复表示输入不合法，乱序应立即暴露。Run ID、精确 Event schema_version、规范字段、状态转换、调用与结果配对也都要核对。给未来版本按旧结构解释，可能把语义不同的数据当作已经发生的效果。

Event 版本、checkpoint 版本、模型录制版本和 Codec 版本是不同协议。一个 Codec 能安全解码数据，不代表其中事件语义被支持；同样，合法 Event 不能证明旁边的 checkpoint State 就是其投影。没有迁移函数时应显式报错，而不是直接写回版本 1。

L06 第 4 节的两层 ID 反例有不同预期：修改 Event 的 `data.operation_id` 返回 `{:unexpected_operation_id, "call-001", "other"}`；保留 Event ID、只修改 `tool_result.v1` 封装内 ID 返回 `{:invalid_tool_result_envelope, "call-001", "mock_write"}`。原例的 `%{"receipt" => "historical"}` 是 opaque 业务数据，不含配对身份；给它新增普通 `"operation_id"` 字段不会自动启用封装协议。终态后即使 seq 连续也返回 `{:terminal_run, :succeeded}`，checkpoint 增加未知字段返回 `:invalid_checkpoint`，单独增加 `last_seq` 返回 `:checkpoint_state_mismatch`。这些错误分别检查身份、转换、形状与状态位置，不能用一个泛化的“坏数据”替代解释。

## checkpoint 解决什么

checkpoint 保存某一历史前缀的 State、seq、原始 Kernel 选项与前缀/状态 hash，自己的形状和版本也需验证。后续 tail 必须从 seq+1 开始并通过原有状态规则。checkpoint 位于 waiting_tool 或 blocked 是合法情况：它描述观察边界，而不是完成承诺。

独立 checkpoint + tail 无法自行证明 checkpoint 来自哪份权威前缀。若攻击者同时改变 State 和 State hash，一个仅检查自一致性的函数不能凭空发现原历史。数据库加载会读取完整前缀，重新构造 State，并核对 checkpoint 的绑定；当前冷路径没有减少读取成本的承诺。以后若要用可信 checkpoint 跳过旧历史，需要明确独立信任锚点与保留策略。

最新 checkpoint 损坏时必须明确拒绝。悄悄退回全量可以让请求暂时成功，却隐藏了坏数据；显式全量模式仍可用于审计和定位，但它不是 checkpoint 模式成功的证据。checkpoint 创建不截断 Event，也不修改原 Run/Event/意图。

## 输入 capture 与结果录制为何分两次提交

输入必须先留档再调用 Provider，否则崩溃后无法知道实际使用了哪份上下文。模型结果则在完整响应通过规则并被接受时，与对应 Event、Run 和下一调度意图一次提交。两次事务之间允许存在未使用或没有已接受结果的输入 capture。

录制是完整响应及其输入绑定，不能把 :done 前的文本/JSON 片段当作结果。取消、Provider 错误或预算拒绝可以有流式观察和输入记录，但没有可复用的已接受模型录制。记录全体尝试是另一套请求/网络审计协议，不能根据本表缺少行推断模型从未被调用。

内存旧 Mock 允许参数 Map 含 PID、reference、函数或任意 struct。它们仍可按原协议完成合法转换，但不能进入严格 inert 的 Recording；Runtime 不伪造录制成功，而在 `snapshot.recording_errors` 中追加 `%{input_seq: ..., event_seq: ..., reason: {:invalid_recording_payload, detail}}`。普通 inert 结果继续完整录制，PostgreSQL 的 Codec 和事务约束不放宽。这也说明内存可运行值不等于跨进程可留档数据。

ModelResultStore 读取需核对三方：封装与行投影、ContextStore 精确 payload、实际接受的模型 Event。工具提议必须与 tool_requested 全值一致，最终输出必须与 run_succeeded 一致。若仅检查 response hash，那么未接受候选或别的 Run 的结果也可能被错误复用。

## Recorded 与重建的区别

Recorded 在宿主明确调用时按精确输入 hash 返回保存的 response，支持离线 Provider 合约测试。它不会调用原 Provider，也不会自行执行工具；但其返回值可能是一条工具提议。若宿主把它送入正常执行流程，之后的工具调度仍可能有副作用。

History 完全不需要 Recorded。Event 已经保存经过接受的业务事实，重建不必重新问任何模型适配器。把 Recorded 调用数也要求为 0，能防止把“没有调用在线模型”误当成“没有再次推理或执行”。精确输入绑定也意味着它不是语义缓存：修改消息、权限、任务或回执后，旧结果应拒绝匹配。

## 提交前后崩溃如何判断

| 写入 | kill 在 COMMIT 前 | kill 在 COMMIT 后、ACK 前 |
| --- | --- | --- |
| checkpoint | 本次 checkpoint 不存在，已有 Run 不变 | checkpoint 已保存且可完整验证 |
| 模型结果事务 | 原 Run/Event/意图，无本次录制；capture 可已存在 | 新 Run/Event/意图与录制同时存在 |

ACK 丢失不是回滚证明。提交后 writer 被 kill 时，数据库事实已前进；调用方应读取并验证事实，不能以没收到成功响应为理由重发工具。真实 kill 测试不能放在全局回滚 Sandbox 中，不然测试观察的是外层事务而不是 API 承诺的提交边界。

这些 hash 和关联校验提供损坏发现与可重建性，不提供抵抗同时重写全部权威来源的真实性保证。safe ETF 负责 inert 解码与边界，语义校验负责顺序、版本与配对；两者不可互相替代。跨 VM 数据继续使用字符串，不增加 unsafe 解码回退。

## 本周完成后的边界

父进程将原 State 通过 safe Codec 编码传给独立 BEAM 进程；子进程在 trace 审计范围内用 `===` 比较全量重建、checkpoint 重建与 expected State，返回比较布尔值和 hash。同时 Provider 和工具调用计数都为 0，才证明本周目标完成。hash 可用于审计，但不替代本次全值比较。它没有恢复 Runtime 的活动流、运行时预算、Provider cursor 或文件效果台账，没有执行 pending intent，也没有自动消除 unknown。安全自动续跑仍需后续调度与效果协议，不能仅凭一个完整 State 启动并重复外部操作。

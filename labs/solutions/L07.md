# L07 参考解答

建议先完成实验再阅读。实际测试计数和故障注入产物以 [第 8 周验收记录](../../docs/validation-week08.md) 为准。

## 重建只是恢复的第一步

History 从已接受事实重建 Kernel State。它能证明当前 pending operation、结果和终态，却不知道正在进行的外部请求是否已经产生效果，也不能从 Event 数量推导 Provider 游标、所有请求开销或原 deadline。

Recovery 需要额外持久保存执行配置与进度。`load` 只读；`step` 取得当前调度意图的有效推进资格后处理一步，`resume` 则执行到完成或暂停。旧 Run 缺少 Recovery 配置时，返回 `:run_not_resumable` 是正确结果；用默认配置填空可能改变原授权、预算和模型序列。

原 RunServer 的手动执行模型保持不变。一个新 Recovery 驱动能安全续跑自己创建的任务，不代表原有每条历史都已自动升级为可续跑。

## pending、claim 和 fence 分别解决什么

pending 意图把下一步工作与 Run/Event 一起提交，避免状态已经推进却没有后续工作。claim 在多个竞争者中选择当前 owner。lease 为失联 owner 提供接管边界，generation token 让数据库拒绝旧 owner 的迟到提交。

owner 字符串不是代次。相同 owner 名字可以被新的进程复用；旧进程也可能在 lease 到期后恢复。因此每次结果提交都要核对意图仍 pending、Run/seq 对应、owner/token 相符并且资格没有失效。续租与释放也必须验证原资格。

取消会 supersede 当前 pending 意图，迟到模型或工具结果不能覆盖取消终态。取消不是撤销已经发生的外部效果；工具回执或外部账本可能继续表明效果存在。

claim 的事务应短，不能持有 Run 行锁等模型网络响应。本周有界本地 Mock/Files 在短临界区重新核对资格并执行，抑制取消与接管竞争；Mock 效果事务仍独立于最终 Runtime 结果事务，文件替换也不能随 PostgreSQL 回滚。把这种本地临界区直接扩展为等待任意远程 API，会扩大阻塞与断连窗口。

## operation 不能与 attempt 合并

operation 标识一次稳定业务意图，绑定 tool 和精确参数。attempt 表示一次投递或查询。把每次重试的 attempt ID 当幂等键，会让外部系统把每次投递视为新业务，失去去重能力。

正确的重复投递保留 operation ID 和参数，新建 attempt。持久 Mock 以稳定操作身份原子保存效果与回执；同值请求返回原回执，同 ID 不同参数明确冲突。业务效果数应保持 1，attempt 数可以大于 1。

运行结果 Event 是 Runtime 接受的观察。外部效果与这个 Event 之间没有共同事务，故而没有结果 Event 不意味着没有效果。仅依赖 Runtime 内存去重，只能在该进程存活时有效，跨 VM 的恢复必须能读取持久外部事实。

## lost receipt 必须先核对

工具调用超时或回执丢失时，正确结论是 unknown。对于支持权威查询的 Mock，以原 operation 身份查询可以取回已提交回执，然后把同一结果提交为 observation 或 reconciliation。查询不应增加业务效果计数。

查不到结果也要看能力契约。如果旧请求仍可能到达，或者查询的是临时缓存，`not_found` 不能证明没有效果。只有外部系统保证稳定幂等键与一致的去重记录，才可能安全地在相同 operation 身份下再次投递。

文件系统没有自动获得这些性质。文件内容相等只能说明当前观察，不能证明哪个 operation 产生了它。准备记录已存在、回执不存在时，新进程可能无法区分“尚未执行”和“已经替换文件但回执没保存”。本周让这种操作 unknown 阻塞，等待明确人工核对；这比猜测后重发更忠于现有证据。

人工核对是新的事实，需保留原 operation、attempt 和 unknown 记录，并以 expected seq 提交。不能直接把数据库 State 改成 running、删掉旧 attempt 或换 ID 重发来掩盖歧义。

## 模型游标和预算也有崩溃窗口

离线 Scripted Provider 的原始脚本与 cursor 都必须持久保存。已接受模型结果、相应录制、业务 Event 与 cursor 推进必须处在一致提交边界；COMMIT 后 ACK 丢失时重新读取，不再次消费同一响应。未完整完成的 attempt 不成为可复用模型结果。

请求 attempt 和资源预算独立于已接受 turn。一个失败请求也可能已经输出字节或占用资源，不能只数 `turn_count`。调用前持久扣除一次 attempt 机会，每帧 ACK 前扣除字节和请求帧数；崩溃后已扣字节不退还。新 attempt 的帧数重新开始，累计字节、总 attempt 上限与绝对 Run deadline 不重置。重启是在同一个 Run 的约束下继续，而不是重新获得配额。

本周离线能力不等于真实模型连接恢复。真实网络请求中“厂商已完成、客户端尚未收到”的费用和结果，需要独立请求 ID、幂等或查询契约；本实验没有从本地 script 的确定性推导这种保证。

## 怎样证明恢复不依赖旧进程

真实 kill 后从独立 BEAM 读取数据库，使用保存的 Recovery 配置继续。比较完整 State 与历史中的 operation/receipt，检查 cursor、预算和 deadline 的连续性，同时读取持久 Mock 效果数。只在同一个 GenServer 中清空一部分字段再调用函数，会遗漏 ETS、进程字典、缓存和未提交连接依赖。

故障探针应由 hook/gate 确认位置后 kill，分别覆盖 claim、request/attempt、外部效果、结果 COMMIT 与 ACK。每个探针同时检查允许保留的事实与禁止出现的额外效果。尤其是 COMMIT 后 ACK 前，caller 的退出不能让已接受结果被消费两次。

History 与 CheckpointStore 的原有零 Provider/工具计数测试继续运行。恢复允许显式 step 产生新效果，不能让只读 load/rebuild 偷偷执行待处理工作。

## 本周能力边界

每个意图的最小 lease 与 fencing 解决安全接管前提，没有实现调度公平性、优先级、常驻 dispatcher 或完整 worker 管理。持久 Mock 演示明确去重契约内的单次业务效果；它不使任意外部服务具备 exactly-once。

文件效果与 PostgreSQL 无共同事务，人工核对仍是必要边界。保留 unknown、返回冲突或拒绝缺少配置的旧 Run，都可以是成功保护系统的行为；把每种故障强行推进到 succeeded 并不是恢复正确性的标准。

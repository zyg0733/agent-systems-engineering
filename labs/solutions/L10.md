# L10 参考解答：持久 Queue 与多 Worker

对应第 11 周。可执行入口、实测数量与证据见 [第 11 周验收记录](../../docs/validation-week11.md)，设计依据见 [ADR 0010](../../docs/adr/0010-background-scheduling.md)。本解答解释验收的不变量，不能用手写期望值代替运行结果。

## 1. 为什么队列可以从数据库恢复

Run、Event 和下一调度意图本来就共享一次提交。Scheduler 不需要另建一份内存队列作为事实来源；它周期寻找已提交、当前且符合资格的意图。Wake 只是提示，丢失后仍有后续扫描，重复后仍须重新原子领取。

新进程启动时不需要旧 Scheduler 的 PID、mailbox 或计时器。已经提交的 intent、Recovery 配置、cursor、attempt 和 due 足够决定下一步；未提交的事务不成为任务。未登记的旧 Run 不被猜测为可恢复任务。

## 2. 为什么多消费者不会获得重复有效资格

未入队 Run 的领取先用 `FOR UPDATE SKIP LOCKED` 锁 Run，再锁其当前 pending intent；命名队列的领取先锁 Queue，再按 Queue → Run → Intent 排序。续期、release 与普通业务提交在 Run 锁内校验当前 Intent，不反向补取 Queue 锁。筛选再次检查 seq、状态、租约与 retry due，然后在同一事务中更新 token、owner、generation 和 expiry，COMMIT 后才返回。

一个消费者获得锁后，其他消费者可以跳过该 Run 并领取别的 Run。它们无法同时为相同当前意图提交有效 claim。提交业务结果时仍验证 token 与 generation；只靠领取互斥而没有写入 fencing，会允许旧 Worker 在失联后覆盖新事实。

`{:ok, nil}` 只说明本次没有符合资格的工作。数据库失败、版本错误与损坏记录要保持错误可见，不能统一改写成“队列为空”。

## 3. 为什么续期不会获得新执行代次

续期证明同一 token 仍然有效，再将数据库 expiry 向后延伸；owner、token 与 generation 保持不变。业务步骤使用的旧 claim map 中即使仍显示初始 expiry，提交校验也以数据库中的同一资格及当前时间为准，不能仅凭内存时间判断。

如果租约已到期，续期必须拒绝，不能把原 token 重新激活。新领取产生新 token/generation，旧结果无法提交，也不能释放新 owner。长步骤的续期者必须与执行者生命周期绑定，不能在业务进程已经退出后无休止延长僵尸 lease。

取消可以使原 claim 立即失效。停止未来本地执行不等于撤销真实目标效果，结果不明仍进入原 unknown 协议。

## 4. 为什么到期前反复 wake 不会增加尝试

失败记录、Retry due 与意图的 `available_at` 提示在同一事务中更新。领取在 Run 锁下读取原 journal，再判断绝对 due。提示字段用于发现，不能授权提前执行，也不能让旧 NULL 或错误的推迟值永久隐藏到期任务。

due 前无新有效业务领取，Retry attempts、模型 attempts、cursor 与录制数均保持不变，执行槽位不会为了退避一直睡眠。到期后再次扫描，取得新的当前 claim，再由 RetryStore 预留下一 ordinal。重启后沿用原 due 和首次尝试时间；如果已耗尽，按照持久策略停止。

## 5. 为什么重复投递仍须检查工具能力

重复 wake 或扫描不会绕过 claim；Worker 死亡后确实可能出现新的 delivery。已确认模型结果对应已前进的 seq，已确认工具 receipt 也可以复用。新的执行者必须重读持久事实，不能盲目从旧步骤开头再执行。

幂等 Mock 的稳定 Run/operation 与参数绑定使重复 delivery 的目标效果仍为 1。对于无回执、不可查询的文件或外部业务，lease 到期不能证明没有效果，正确路径是 unknown → blocked → 可见核对队列。后台调度器排除 reconcile 意图，既不自动查询，也不再次投递该业务。

## 6. 有限 Worker 具体限制什么

一个 Worker 处理一个已领取步骤，完成后将槽位交还，再竞争下一意图。Scheduler 的 `workers` 限制其在途步骤数；两个独立 Scheduler 的总容量是配置之和，并非全数据库只有一个全局信号量。

优先级 0—9 在 Run 创建时固定，值大者先考虑，同级按意图 ID 排序。它不抢占已在执行的步骤，`SKIP LOCKED` 与并发时序也不保证完成顺序。持续高优先级输入仍可能使低优先级任务饥饿；公平性与背压不能仅用有限 Worker 数宣称已经解决。

## 7. 保护断言

| 有意破坏 | 应触发的失败 |
| --- | --- |
| 先查意图，事务外再写 claim | 同一意图并发领取获得重复有效资格 |
| 锁 Intent 后再锁 Run | 与既有提交路径交叉时可能等待或死锁 |
| Worker 再调用 `Recovery.step(run_id)` 二次领取 | 与自己已持有的 lease 冲突 |
| 只使用 `available_at` 判断 retry due | 旧 NULL / 提前 hint 导致提前尝试，推迟 hint 隐藏到期任务 |
| 续期时更换 token/generation | 在途业务步骤变成不匹配的旧资格 |
| 到期后允许原 token 续期 | 旧 owner 可能覆盖 successor 或释放其 lease |
| 用进程重启时间重算 due | 退避被延长或重试窗口被重置 |
| 将 reconcile 放进普通执行扫描 | unknown 自动重发或无授权查询 |
| 每次 wake 都启动无界 Task | 重复提示突破并发上限 |
| 工具 receipt 后崩溃就重发业务 | 已确认回执不复用，目标效果可能重复 |

下一阶段仍需用操作系统暂停/恢复、真实数据库断连与受控目标 fencing 验证更广的失效模型。第 11 周通过的是本仓库声明能力下的持久发现、有限并发、真实续期和到期再领取。

# L05 参考解答

建议完成实验报告后再阅读。本解答解释不变量和预期观察；实际计数、payload 字节与本机结果以 P1 产物及 [第 6 周验收记录](../../docs/validation-week06.md) 为准。

## Session 和 Context 为什么分开

Session 是完整、可追加的规范记录，Context 是某次请求的派生投影。若直接把压缩结果写回 Session，之后就无法区分原消息和摘要，也无法发现摘要有没有漏掉条件。本实现从不因裁剪修改 Session；`Session.append/3` 只增加一条有稳定 ID/序号的消息，保留事实、验收与约束字段。

`user`、`assistant`、`note` 是宿主声明的叙述角色，不是信任等级证明。模型说“我写完了”不会自动得到工具回执，传 `assistant` 也不改变 Kernel。Session 不接收 `system` 或 `tool` 角色，工具观察从 `Run.operations` 获取，能力从宿主配置获取。宿主若要保留模型回答，应明确调用追加 API，并为其内容负责。

| 实验问题 | 预期结论 |
| --- | --- |
| 历史消息宣称获得 shell/网络 | permissions 保持宿主值，未新增能力 |
| 摘要宣称写入成功 | 只是非可信叙述，不能覆盖操作回执 |
| 最旧消息省略 | manifest 保留 ID、seq、源 hash 与 omitted 归属；完整文本仍在 Session |
| `unknown` 工具回执 | 整个操作与原结果精确保留，不改 outcome，不推断外部效果 |
| 保护内容本身超限 | `protected_context_too_large`，不调用 Provider |
| 流式回答部分输出 | 临时流数据，不自动追加规范消息 |
| capture COMMIT 后崩溃 | 输入留档存在，但是否发出请求/收到结果仍未知 |

## 裁剪和摘要如何工作

完整 payload 能放下时，不裁剪、不创建摘要。超过预算后，先保留不超过 `keep_recent_messages` 的近期完整消息后缀；若仍超限，依次去掉后缀最旧的消息。工具调用和结果不参加这条裁剪路径，它们完整地留在 operations 中，因而不会出现“工具调用保留、结果被截半”的结构。

旧消息的摘要是 `extractive_prefix.v1`：按规范顺序拼接带 ID/seq/role 的旧消息文本，再取 UTF-8 安全前缀。它不调用 LLM，不把文本改写成新事实，封装标为 `untrusted_session_narrative`。摘要 source IDs 只能是被省略的消息，hash 绑定完整旧消息列表；摘录有限，不承诺每条旧消息都有文字出现在摘录中。想查完整内容，应回到规范 Session。

实际预算使用 `byte_size(:erlang.term_to_binary(payload, [:deterministic]))`，整个摘要封装也受 `max_summary_bytes` 限制。相同汉字按 UTF-8 字节计量，不按字符数或 token 计量。保留消息优先于摘要；预算只够保护内容和近期消息时，可以没有摘要，但 manifest 必须明确 `omitted_budget`。这比悄悄删除回执或硬约束更容易审计。

## 保护内容与校验

保护内容包括原 input、Run 身份与轮数、完整 operations、Session 身份和版本、task facts/acceptance/constraints、完整宿主 permissions 与 available_tools。保护内容无法容纳时，任何摘要算法都不应伪装成成功；必须报告所需字节和预算。调用方需要调整预算或缩小任务/工具结果的来源范围，不能让压缩器自行弱化事实。

`Context.verify/5` 不只核对 payload hash。它使用传入的权威 Session、Run、permissions 与有效策略，重新执行确定性构造，全量比较 `%{context, manifest}`。因此改了 excerpt、phantom source ID、included/omitted 列表、保留证明、源消息或策略，都会导致不一致。即使某条消息被省略且摘录没有覆盖它，完整源 Session hash 仍会改变。

Context 对 Run 先做 inert 编码检查，再通过一次丢弃结果的纯 Kernel 取消命令复用完整状态规则；合法终态通过 Kernel 的 `terminal_run` 响应被接受。此校验不写 Event、不修改源 State、不执行工具。非法 status、序号、操作形状、pending 指针与配对封装会被拒绝，不能因为它们可以序列化就把伪造操作当作事实。

这些 hash 不是数字签名。若攻击者能一致地重写所有原始记录和派生数据，本实验没有外部可信锚点替你鉴别真实性。此处的价值是可重建、可发现不一致、明确来源与数据边界。

## Runtime 和 PostgreSQL 的边界

Runtime 的 `append_message/3` 是宿主 API。流式请求进行中返回 `busy`，终态返回 `not_editable`；内存模式使用纯 Session.append，关联规范 Session 时使用 SessionStore.append 的 expected version。另一个 writer 先提交后，旧版本 writer 得到 `stale_session_version`，不会静默覆盖。

Provider 接收的是 `built.context`，不接收整个 built 或 manifest。snapshot 中保存最近一次输入证据；模型响应提交后，Run 已前进，snapshot.context 仍对应推理开始前的 Run。核对时应重建那一时刻的 Run，或使用 ContextStore 中保存的来源；不能拿最后终态替代输入快照。

ContextStore.capture 在事务内核对当前 Run 的完整状态/序号，以及可选关联 Session 的版本与完整内容，然后一次提交来源、payload 和 manifest。成功 ACK 在 COMMIT 后，Provider 才启动。capture 事务失败时不消耗 Scripted Provider 项；同一 Run 序号可以存在多份输入审计记录，它们不是业务 Event，也不是“只执行一次”的请求台账。

Session 之后追加不会使旧 capture 失效；旧 capture 保存的是历史源输入。新 capture 用旧关联 Session 则应被拒绝。读取 capture 会安全解码、核对行投影并确定性重建，不调用 Provider 或工具。P1 的 Run/Event/意图 kill 探针验证已有业务提交边界，ContextStore 测试另验证自己的提交前后 kill；它们不提供横跨两个事务和外部工具的原子性。

## P1 应怎样审查

P1 默认 PostgreSQL 路径使用 40 条规范消息，四份压缩模型输入都有提取摘要。每份 manifest 字节不超过 16384，facts、验收、约束与宿主权限始终原值保留；operations 从空集合增长到三个已配对工具结果。规范 Session 仍为 40 条，版本未因推理或摘要增长。

修复仍是固定配送费 fixture：`subtotal > 100` 改为 `subtotal >= 100`，验收 3/4 变成 4/4。三次文件调用分别读取、patch 和写修复说明；差异与前后 hash 由真实工具结果给出，摘要不生产这些事实。宿主只在源码与测试匹配固定受信任版本后运行验收，没有向模型授予 shell。

取消实验停在未完整 JSON 参数处。没有接受工具提议，因此 operations 为空、写入数为 0，Provider worker 被回收；数据库终态没有待调度意图。此结论不能推广为“任何取消都能撤销已完成写入”：已发生效果仍是 Run/工具台账中的事实。

完整输入 capture、Run 事件与 diff 让 P1 可审查，但 P1 使用的教学 RunServer 路径尚未实现 Provider cursor/流/预算计数的跨重启恢复、持久文件效果台账与安全自动续跑。后续持久 Recovery 使用另一套登记、预算和核对协议。离线脚本流证明流程闭合，不证明真实模型一定会修复同类任务。

# L15 参考解答

对应 [MCP stdio 实验](../L15-mcp-stdio.md)。实际结果、计数和后端以 [第 16 周验收记录](../../docs/validation-week16.md) 为准。

## 1. 为什么固定 2025-11-25

这是本周实现并验证的明确协议边界。该版本使用 initialize/initialized 握手；2026-07-28 已移除握手，版本和能力随每个请求的 `_meta` 发送，发现能力使用 server/discover。两个版本不是只更换日期常量就能互换。客户端应拒绝不支持的版本并关闭连接；未来实现新版本需要独立协议分支和验收，不能在旧初始化失败后静默切换。

stdio 的 newline framing 与 JSON-RPC 请求配对仍需各自验证。收到一个可以 JSON.decode 的对象，不说明其版本、消息类型、ID 或生命周期阶段正确。

## 2. 工具发现为什么不能赋予权限

服务器控制 tools/list 的名称、schema、描述和 annotations；它们属于不可信远端数据。宿主预先批准确切名称、输入约束与模型可见描述，并用完整分页结果进行精确核对。额外工具保持未批准；缺失、重复或 schema 漂移需要中止。服务器标记 readOnlyHint/idempotentHint 不能获得文件、网络或非幂等重放权限。

同一个远端工具名在不同 server 名下形成不同局部名字。只核对后缀或前缀会让命名碰撞变成权限穿透。

## 3. 为什么不直接接受任意 JSON Schema

未知关键字如果被忽略，宿主以为生效的约束可能根本没有执行。`$ref` 解析、正则和组合器还会引入独立的资源与外部访问面。本实验在策略安装时拒绝未支持能力，并要求显式 closed object；schema 和参数都受深度、节点与大小上限约束。这个有限 validator 不能宣称完整 2020-12 conformance，第三方工具必须适配已支持子集或等待更完整的独立实现。

## 4. 为什么 timeout 与 cancelled 都是 unknown

服务器可能先完成效果，再丢失回复、暂停或忽略取消通知。取消是 advisory，发送成功不表示服务器没有执行，也不会撤销文件修改。正确做法是保留原 operation 身份、连接/请求身份与故障证据，结束污染连接，交给核对流程。迟到回复不能随意配到下一个请求，也不能抹去已经对外暴露的 unknown。

initialize 不可按普通工具请求取消；握手失败应结束传输，不发送针对 initialize 的 cancelled 通知。

## 5. 协议错误与工具错误有什么区别

合法 JSON-RPC error 有原请求 ID 和 code/message，表示收到确认的协议层错误；合法 result 中 isError=true 表示收到工具层失败内容。二者都有可配对响应。断连、错误 ID、非法 JSON 或超大消息则可能使已发送调用无法确认，不能伪造为同一种“未执行”的业务失败。

映射时保留原始有界错误信息，同时沿用 Runtime 的失败分类；远端文本不执行、不提升权限，也不改变重试策略。

## 6. 如何验证恢复不会重放效果

使用固定 after_effect_drop server：先收到真实工具调用，再向本次 workspace 文件追加，最后在响应之前退出。确认效果出现一次，原调用进入 unknown，核对队列可见。随后新建 BEAM 进程恢复同一 Run，观察 operation ID 不变、没有新增工具调用或第二次追加。对于已经提交回执的重复投递，直接复用原回执，不再发现或执行远端工具。

MCP request ID 只负责连接内响应配对；持久 operation ID 负责跨恢复身份。不能拿新连接的新 request ID 当成“新的业务操作”绕过未知结果处理。

## 7. 为什么 MCP 进程仍需要隔离和实际清理

协议本身不约束 server 的 open/connect/fork。stdio server 仍在 W15 默认拒绝的 Seatbelt 下执行，只允许固定命令和私有 workspace，禁止网络与创建新目标进程。stdout/stderr 与可信监督器控制帧分离，防止 server 伪造退出证明。

关闭要检查自己拥有的 OS target 与 guardian 实际退出；Task DOWN、关闭 Port 或返回 timeout 不能单独证明这一点。进程被收回也不能撤销已发生效果，lease/fencing、预算和 unknown/reconcile 必须继续执行。

# L21 参考解答

六章覆盖状态机、Agent Loop、Session、Event History、外部效果、Lease。原计划章节编号保持不变，现行实验用明确链接映射；不能因计划表仍写 L04 就把 Session 读者引向文件工具。

源码导出应排除旧运行时、依赖、编译结果、数据库与产物。安装 archive 和 Hex/Rebar3 构建工具可以作为声明的 warm cache，但必须独立记录 hash 与来源；不能把复制现成 deps/_build 称为从零构建。本实验重新解压运行时、从 PostgreSQL 源码编译全新 prefix、创建独立 cluster 并重编依赖，仍明确只验证同一宿主。

DATABASE_URL 优先于 PGPORT；未 unset 就可能悄悄连接原库。长期 export LAB_DATABASE_ENABLED=false 也会让下一节数据库实验不启动 Repo。环境计划须清理继承项、绑定新路径、明确 test/dev 环境和 Scheduler 状态，空库/cluster identity/21 次 migration 都要有实际证据。

只检查输出路径字符串不够：大小写不敏感文件系统上的 LIB 可以指向 lib，Unicode 别名也可能指向同一实体。创建目录前要检查已有祖先的实际设备/inode，拒绝时源 inventory 必须保持相同。先 mkdir_p 再查 symlink 会在拒绝前留下子目录，同样不是完整拒绝。

协议 hash 只能证明内容自洽，不能证明六章真的符合约定。还需与冻结导出中的 suite、完整 manifest 和精确 assets 集合绑定。报告重算时也要先验证旧报告完整结构/hash，不能覆盖损坏记录来“修复证据”。单条 JSON 上限和汇总上限必须分开：五条合法反馈可能大于单条上限。

空模板、作者、代理和自动脚本均不计作外部人。工具能检查独立性声明、重复 ID、完整章节、固定复现步骤和 blocker，但不能认证实际身份或证明自报命令真实执行。可信宿主需核对原始记录；没有真实反馈就保持 0 人与 P5 false。technical passed 与 external pending 可以同时为真。

全量测试与六个主实验分别验证：状态不变量、Context 保护事实、无效果的只读重建、实际崩溃后安全续跑、旧 Worker 恢复后的提交拒绝、旧历史升级/备份还原。沿用权限、预算、deadline、回执、unknown 和审批合同，不为通过实验重置额度或换 operation ID。归档日志和失败窗口，清理只针对本轮拥有的 cluster。

## 解答勘误

独立复核发现 [L05 解答](../labs/solutions/L05.md#p1-应怎样审查)将 16,384 字节预算称为 manifest 大小。实际 [P1Demo](../lib/agent_systems_lab/p1_demo.ex) 与 Context 限制的是 Provider payload 的确定性 ETF 编码；`manifest.byte_size` 记录该值，独立 manifest 的 JSON 文件大小不计入预算。本批只修正解答，没有调整预算或实现。

审查者另建议为新章中 Provider 游标保持 1 的断言补直接入口，已链接 [RunServer 测试](../test/agent_systems_lab/run_server_test.exs)；不把场景级状态检查冒充游标检查。

技术交叉复核还发现导读责任图将全部权限校验放在意图接受之前，范围过宽。实际 Gateway 先检查工具配置与参数形状，Files/Workspace 在执行阶段仍会核对真实资源、符号链接和内容前置。本批将图拆为接受前预检与执行前复核，并明确 Kernel 接受调用命令后产生 `tool_requested` 事件；已接受意图不等于最终获准执行或效果已发生。

## P3 有界复验与仍未知的首因

第二轮首次 Linux CI 的 P3 返回失败，子报告在原 ExUnit 输出中被截断，原始组件目录随测试清理而删除，无法认证具体故障窗。基准 e335 的改动仅增强失败诊断；后续 CI 通过没有证明该首因已修复。本批未找到可由旧材料确认的业务根因，不凭静态风险认定超时或数据库故障。

为避免持续重跑，本批预先限定最多三次 `lab.p3 --repetitions 1`，每次使用新 BEAM 和全新输出目录。创建本批专属 PostgreSQL 18.6 集群，绑定 `127.0.0.1:55443`，实查 fsync、synchronous_commit、full_page_writes 均为 on；全局 DATABASE_URL 移除，未触碰旧集群或原失败库。

三次均退出 0，四组件完成，audit_complete=true；每次 53 份历史及新 BEAM 审计一致，27 个重建执行入口调用均为 0。共完成 15 个数据库故障 probe 与 15 对真实 SIGSTOP/SIGCONT；没有将这个有限重复写成新的完整冻结矩阵。每次完整组件报告、原始子进程证据、argv、退出码和日志 hash 见 `p3-reproduction/`。集群已关闭，数据与失败调查记录保留。

结论为“本批未复现，首因仍未知”。原诊断能读取失败组件的 `report.json` 及 failed_probe，无需因摘要截断改动 P3 业务实现。返回成功后的后置断言失败、测试超时仍是未覆盖的证据保留路径；这是另一个诊断范围，不能当成原失败原因。后续若复发，先检查新保留的具体故障窗与子进程日志，再决定修复。

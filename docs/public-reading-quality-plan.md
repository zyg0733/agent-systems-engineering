# 对外试读前的教材质量与学习体验计划

制定日期：2026-10-24（Asia/Shanghai）。范围是现有六章正文、配套实验和阅读站；承接[下一阶段计划](next-stage-plan.md)、[试读协议](../book/reader-study/README.md)与[阅读站维护说明](reading-site.md)。这是待执行的质量计划，文中的目标、评分和工时不是已经取得的结果。

## 1 结论与公开范围

**当前适合继续私有准备，修订后开展小范围邀请试读；暂不建议以“完整教材”或“正式 0.1.0”广泛公布。** 阅读站解决了浏览入口，尚不能证明读者理解正确、能够独立完成实验。无需等 30 章全部写完：先让已有六章构成可学习、可验证的闭环，再评估公开“六章持续写作试读版”。也可以先完成前一两章的闭环，但不得将局部试读等同于六章正式验收。

本轮只提交、推送到现有私有仓库并检查 Actions。GitHub Pages 保持关闭，不设置 PUBLISH_READING_SITE，不改变仓库可见性，不创建正式发行 tag。将来公开阅读预览与发行软件版本分别决策；本计划不改写 rc.1、W24/W25/W26 的历史证据或既有发行政策。

| 需要分开的判断 | 当前事实 | 达标需要的证据 |

## 2 先明确读者与学习结果

首批面向熟悉后端开发、测试和基本 SQL，希望理解 Agent 状态、外部效果与恢复机制的工程师。理解系统设计的读者可以先走阅读路线；运行实验的读者还需要 Elixir 值、模式匹配、函数调用和基本 OTP 知识。入口应明确先修，不能暗示这是零编程或零 Elixir 基础课程。先修差距需要补充材料，不能算作读者失败。按目标读者已有知识选择讲解深度，是技术写作的基本要求。[Google 技术写作：读者](https://developers.google.com/tech-writing/one/audience)

先交付一页“适合谁、需要什么、从哪里开始”，附 5 道不计分自测：读懂模式匹配；区分进程与业务状态；解释 SQL 原子提交；区分调用和结果；辨认重试可能重复效果。不熟悉者跳到对应桥接页，而非直接跳进长实验。

六章的学习目标应改成可观察行为：

| 章节 | 读完后能独立做什么 | 最小产物 |
| --- | --- | --- |
| 第 2 章：纯状态机 | 预测合法/非法命令的状态与事件，验证拒绝命令不改变事实 | 一条正常轨迹及错误 ID 的可运行断言 |
| 第 5 章：Agent Loop 与工具 | 区分模型请求、接受提议、执行效果和提交结果四个边界 | 三步轨迹及取消前后的效果对照 |
| 第 8 章：Session/Context | 区分消息、事实和宿主权限，解释本实验 ETF 字节预算的边界 | 一次受保护事实保留/超限拒绝的解释 |
| 第 14 章：Checkpoint | 区分纯重建和续跑、完整性和权威来源、校验和性能 | 状态相等且零新增调用的证据，以及原权威历史不变时自洽伪造 checkpoint 被拒绝的反例 |
| 第 16 章：持久效果与核对 | 画出 prepare、目标效果、receipt、Kernel COMMIT 的不同窗口 | 对 unknown 作出有依据的核对决定 |
| 第 20 章：调度与恢复 | 解释 lease 到期后旧 Worker 为什么仍需持久 fencing | 同 seq 接管及迟到写入被拒绝的证据 |

目标采用“解释、预测、构造、验证”，避免只写“理解”。用小练习及时发现误解，再安排长作业；先修、目标和练习应互相对应。[Carpentries 教学准备](https://carpentries.github.io/instructor-training/instructor/18-preparation.html)

## 4 技术准确性：建立小规模证据台账

先覆盖 12 条高风险主张：拒绝命令不改 State；final 计轮数；rebuild 零执行；Context 的权威来源；ETF 不等于 token；checkpoint 不等于签名；receipt 不等于 Kernel 接受；COMMIT error 不证明回滚；unknown 不等于可以盲目重试；lease 不等于远端终止；fencing 在提交门生效；取消/过期不撤销既有效果。

每条台账至少记录：

1. 主张 ID、章节精确位置、原文与误读后果；分类为项目契约、一般原理、版本事实或测量结论。
2. 前提、失败窗口、反例和不覆盖范围；对应代码/测试入口及 Git SHA 或受验证的源码清单身份。
3. 当前实际执行的命令、环境、日期、原始日志；没有执行明确写待执行，不能只引用测试名称充当运行证明。
4. 一手引用的版本、固定链接和复核日期；上游代码阅读与上游测试执行分开标记。
5. 作者核对、独立技术审校、示例实测、真人理解验证各自的状态，负责人和待修项。
6. 修订后需要重审的章节、代码、例子和问题；保留旧失败与修复后的复验。

当前抽样中，Context 度量、checkpoint 权威边界、受控 Mock 的幂等范围、lease/fencing 的限制与实现基本一致，仍需第二人审校。尤其避免将“受控目标的一个逻辑效果”推广为任意远端 exactly-once，将 hash 写成授权，或将 Linux 核心测试通过写成完整隔离通过。

正文例子按“可逐字执行、解释片段、预期失败、预期输出”分类。人工确认可信的例子清单后才执行；不自动执行任意 Markdown 围栏。保留 shell/IEx 上下文、重置条件、输出目录与数据库所有权。数据库例子在本轮自有实例或明确隔离范围中运行，失败目录保留，不碰共享数据。代码与正文分别取 hash，最终候选重新绑定身份，不能将旧运行直接改写为新提交通过。

两项一手核对的示范：PostgreSQL 的 now() 是事务时间，clock_timestamp() 会随实际时间变化，关系到租约判定；第 20 章的 Oban 比较应固定到研究时的提交，代码阅读不能冒充上游测试已跑。[PostgreSQL 18 时间函数](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)、[Oban 固定提交源码](https://github.com/oban-bg/oban/blob/0704bf0018bfc915560998fbdfb899dd508f5aff/lib/oban/engines/basic.ex#L543-L548)

独立技术同行重点审查数据库提交不确定性、并发 fencing、外部效果三个边界。首轮要求每条核心主张均有第二人结论，且没有未解决事实错误或会导致错误操作的高风险歧义；审阅者不能只复述作者结论。

## 5 阅读与练习的组织

保持四种材料的用途清晰：教程带领完成一次学习，操作手册解决明确任务，参考页查契约，解释页说明原因；它们互相链接。这个划分用于减少初学者在安装细节、历史报告和原理之间来回跳转，不要求重写全部文档。[Diátaxis 的应用说明](https://diataxis.fr/application/)

先修桥接只补足现有六章所需概念，不顺带承诺写完 24 章。第一条路线是无密钥、内存模式的短闭环：预测 demo 结果→运行→解释 requests/effects→构造错误 ID→写断言→重建并检查零新增效果。完成后再进入完整 L01。第二条路线才引入 PostgreSQL、提交边界和 unknown；macOS 完整教学路线与 Linux core 路线分别说明，后者不承诺 Seatbelt 等价能力。

每章开头列目标、先修、平台、预计任务及当前稿件状态；结尾给检查题、常见错误、下一步和参考。先测实际任务耗时再承诺时长，冷下载、编译和安装不混进纯阅读时间。首页应让读者迅速判断已有内容、未写内容、源码如何取得及该选哪条路线；开篇说明适用读者和前置，有助于避免错误预期。[Google 技术写作：文档组织](https://developers.google.com/tech-writing/one/documents)

第一版术语表至少覆盖 state/status、command/event、rebuild/replay/resume、operation/attempt/receipt、lease/heartbeat/fencing、unknown/error。每项给中英文、代码符号、首次定义、易混对照与最小反例，优先统一定义再做全文措辞调整。

## 6 网站阅读体验验收

本地已有窄屏、搜索、复制、深浅色、最近章节与图渲染检查。这些是技术可用性证据，尚未验证真实读者的检索成功或学习成效。公开预览前执行下列矩阵，逐项保存环境、结果、失败与修复：

| 场景 | 具体任务与通过条件 |
| --- | --- |
| 路线与导航 | 从首页找到先修、L01、unknown、平台限制；章间前进/返回、刷新深链接均可用；当前状态与历史报告能区分 |
| 搜索 | 用真实问题查“写入了但没收到响应”“旧 Worker 还能提交吗”等，而非只输入标题；记录首次结果能否解决问题、改词次数及未命中词 |
| 键盘与焦点 | Tab 顺序合理；搜索可打开、输入、选结果、Escape 关闭并返回触发点；无键盘陷阱，焦点可见且不被固定导航遮挡 |
| 窄屏与缩放 | 320 CSS px、移动设备与桌面缩放核查；正文/控件不需横向滚动，长代码/宽表可在局部滚动；检查 200% 文本放大及 400% 缩放的实际表现 |
| 代码与实验 | 复制内容能区分命令、提示符和预期输出；长行、错误提示、链接与步骤在深浅色下都可辨认 |
| 图与辅助技术 | 每张关键图有表达同一推理的文字；屏幕阅读器能辨识标题、链接与代码用途，装饰图不重复朗读 |
| 对比度与动效 | 实测普通文字至少 4.5:1、大字至少 3:1；检查焦点/控件可辨识、减少动态效果设置；记录工具和未覆盖范围 |
| 最近章节 | 准确显示“最近阅读的章节”，不称学习完成率；清除有效，存储不可用时仍能阅读，无需账号或外部追踪 |

320 CSS px 回流、键盘、焦点、文字等价与对比度分别参考 WCAG 2.2 及解释文档；代码/表格确需二维布局时可局部滚动，外围正文与控件仍需回流。本矩阵只是拟采用的检查项，不是 WCAG 一致性声明。[WCAG 2.2](https://www.w3.org/TR/wcag/)、[回流说明](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)、[非文本内容](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html)、[文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

## 7 真人试读：观察能否独立完成与解释

建议 3—5 名目标读者及至少 1 名独立技术审校者。先安排两次短 pilot，修复明显找路和首次任务问题，再开展六章正式试读；短 pilot 不自动计入正式人数。可覆盖以下背景，允许一人兼具多个特征：

| 读者背景 | 重点观察 |
| --- | --- |
| 熟悉后端、初接触 Elixir 的 macOS 工程师 | 先修判断、首次成功、错误诊断 |
| 熟悉 Elixir/OTP 的工程师 | 概念精度、源码定位、反例和练习深度 |
| 有 SQL/分布式基础的 Linux 工程师 | Linux core 路线、安装材料、支持范围表达 |
| 有 Agent 应用经验且兼用手机的读者 | 状态/效果思维转换、检索、窄屏连续阅读 |
| 可选授课者或使用辅助技术的读者 | 课时、提示/答案、辅助阅读的真实障碍 |

测试任务依次是：① 从首页判断适用路线、版本和未完成内容；② 在运行前预测内存 demo 结果，运行后解释其持久性边界；③ 独立写错误 ID 断言并重建轨迹；④ 完成六章和新情境理解问答；⑤ 至少一人在真实新工作区完成冻结协议规定的主实验及日志。加一个受控错误，如已有输出目录，观察能否安全定位；不得为完成率跳过平台限制。允许查教材，记录作者提示、同行或 AI 帮助，逐步代做的任务不能标成独立完成。

建议预先登记下列 6 题，每题 0—2 分：0 为关键判断错误，1 为结论对但因果/边界不全，2 为结论、证据与边界完整。

| 问题 | 满分要点 |
| --- | --- |
| queued 收到 final 为什么拒绝？ | 前置不符，不产生新事件/seq；错误返回不是 failed 事件 |
| 写入成功但响应丢失，能否换 ID 再试？ | 效果可能存在；须保留原身份，依目标查询/幂等能力或人工核对 |
| 重建状态相等能否证明安全恢复？ | 还要验证零新增模型/工具调用；重建和有资格的续跑分开 |
| Session note 写“已开放网络”会改变权限吗？ | 消息不是宿主权威；压缩同样不能扩大权限 |
| COMMIT 后 ACK 丢失，error 能否证明回滚？ | 不能，需核对持久事实/receipt/seq，避免重复效果 |
| lease 到期为什么还需 fencing？ | 旧进程可能仍活；提交和适用效果端需校验当前身份、代次和有效期 |

拟采用 ≥10/12，且 unknown 盲重试、重建再次执行工具、lease 到期等于旧进程死亡三类关键误解必须修订并复测。评分阈值在正式试读前确认；目前没有任何实际成绩。体验任务另按 0=失败、1=需提示、2=独立完成记录，不混成一个模糊满意度。

记录安装/下载/编译、阅读、执行、诊断各自耗时，查找路径、重读位置、错误、帮助次数和任务后信心。先 pilot 再定耗时预算；以“3/4 人”等实际分子分母报告，小样本不推断普遍成功率。是否“觉得清楚”只是反馈之一，不能代替反例解释和产物验证。

正式计入者必须满足现有[试读协议](../book/reader-study/README.md)的六章记录要求；单章或手机导航参与者只贡献相应 UX 证据。至少一次新工作区实验与新主机冷安装分别验收，不能互相代替。作者/代理不计真人，技术审校者只有另行完成读者协议才可按协议判断是否计入。

沿用现有严格 JSON schema 和冻结协议，不将 UX 自由字段塞入 ReleaseStudy。访谈附件另存匿名 ID、页面/源码/协议身份、任务和观察，并关联正式记录。真人身份由可信宿主核对，hash/JSON 校验不认证人。原始反馈保留，按问题→修订→原读者复验形成闭环，不删除 blocker 来消除阻断。

## 8 分阶段工作包与决策门槛

以下工时是规划估算，不是已测量耗时或日期承诺；真人、冷机器和技术同行的可用性单独登记。建议主要作者每周 15—20 小时，优先修订六章，暂缓同时承诺多章写作和新 Provider 工程。

| 阶段 | 工作与交付 | 估算资源 | 退出条件 |
| --- | --- | --- | --- |
| A，本轮 | 阅读站及本计划提交私有仓库；完成站点构建和既有 Lab CI | 维护者，自动化执行 | 两套适用检查通过；Pages 部署保持跳过；结果绑定实际提交 |
| B，试读准备 | 入口/先修、依赖桥接、首个小任务、当前状态页、术语；12 条主张台账和示例清单 | 作者约 12—20 小时；技术审校约 6—10 小时，依例子重跑调整 | 承诺路线可获得材料；高风险语义有明确结论；可信清单的例子有当前证据 |
| C，短 pilot | 两次 30—60 分钟观察；至少覆盖找路和首次任务，修订明显卡点 | 2 名真人；作者观察/修订约 4—8 小时 | 无阻塞首次任务的问题；形成正式任务、题目与合理时间预算 |
| D，六章私有试读 | 3—5 名真人分次阅读、主实验、问答与问题闭环；完整网站体验检查 | 约 2—3 周协调窗口，非纯工作量；读者实际用时另测 | 正式协议齐全；无未解决 blocker/高风险错误；受影响材料取得复验，理解题达预登记标准 |
| E，公开试读评审 | 冻结待公开内容和源码/稿件身份；核对支持范围、获取方式、反馈与许可；提交具体预览给所有者审阅 | 作者约 4—8 小时，失败修复另计 | 满足下方公开清单，由所有者另行决定开放范围和发布 |
| F，持续写作与正式发行 | 根据试读卡点优先补桥梁章节；分批扩充正文；最终候选按既有政策重验 | 按[下一阶段计划](next-stage-plan.md)资源排期 | 全书完整度、网站预览、软件发行分别记录，不因其中一个通过而自动放行其余 |

若 B 超出一个作者周，就拆分，不压缩审校；D 缺真实参与者保持 pending，继续可独立推进的编辑与例子核对。本轮不代发招募、不联系读者，也不自动安排未来任务。

公开六章试读版的建议清单：

- 标题和首页准确标注“六章持续写作试读版”、日期/版本、未写章节、适用读者与平台。
- 六章关键主张有独立技术结论；所有宣称可运行的例子有当前稿件证据，未解事实错误和高风险歧义为 0。
- 对外承诺的学习路线在无原作者逐步帮助下完成，正式试读与关键理解题达到已登记标准，blocker 均有修订和复验。
- 公开内容采用明确清单。当前生成器会收集 book/labs/docs 的 Markdown；隐藏导航或搜索不等于禁止访问。先区分当前指南、历史报告、维护材料，逐页决定是否纳入，不将历史文档改写成当前通过记录。
- 私有源码下必须明确实验材料获取方案：只读预览、授权源码包、独立公开配套仓库或全仓库公开需要分别决定，本计划不授权改变可见性。
- 站点关键导航、中文检索任务、窄屏、键盘与图示文字验收完成，剩余限制如实列出；轻量纠错入口可以使用。
- Apache-2.0 / CC BY 4.0 的边界、署名和第三方引用复核；公开预览配置与 Pages 账号条件单独核对。
- 所有者对这份具体预览与范围作明确发布决定。即使公开网站，正式软件仍保持其实际发行状态，不能跳过冷主机、完整 Linux、最终冻结矩阵和既有批准门槛。

## 9 后续如何判断值得继续投入

优先看读者是否能独立预测、验证、解释失败并正确划定保证范围，其次才是界面偏好或访问量。首轮结束交付一页质量报告：参与者与完成范围、实际任务结果、关键误解、按严重性排序的问题、修订/复验、技术台账覆盖、未覆盖平台和下一步。没有测量的项目写未测，不填成功率。

用该报告决定先补哪一章、哪一个诊断步骤、哪一个桥接概念。段落进度、笔记、离线阅读等增强功能只有反复出现需求时再做。这样可以先交付可信、可学的少量内容，再逐步扩成完整教材。
